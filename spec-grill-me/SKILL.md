# spec-grill-me —— 批量追问，一次收敛

## 何时用

用户带着一个**还没定完的方案**来，想被追问，而不是想被夸奖或直接执行。典型触发：`grill me`、`拷问我`、`这个设计有什么问题`、`帮我把方案想清楚`。

不适用：用户只要执行（直接做）；用户要的是普通问答；用户只需要一条评审结论而不需要收敛整棵决策树。

与 `spec-create-requirements` 的分工：本 Skill 是通用的方案 / 架构 / 计划决策追问，不限定交付物；当用户要把需求收敛为 PRD 与交互原型时，走 `spec-create-requirements`，不在此重复其交付流程。

## 目标

不是“问很多问题”，而是**批量走完决策树**：

1. 先由 Agent 做足调查，列出真正影响实现的决策点。
2. 按依赖层级批量提问，每个问题同时给出可选方向、推荐答案、依据和代价。
3. 默认把推荐答案作为“暂定建议”继续推演，不要求用户逐题作答。
4. 最终输出一份完整建议列表，由用户一次性确认或按编号修正。
5. 只有用户明确确认后，建议才升级为“已确认决策”。

Agent 负责降低决策成本，用户保留最终决定权和纠错权。

## 核心失败模式

1. **一次只问一个问题** → 用户疲劳、吞吐低，也看不到各决策之间的依赖。
2. **只提问不给建议** → 把所有分析成本重新推回给用户。
3. **推荐没有依据** → 用户无法判断该采纳还是修正。
4. **用户改了一项，却不重算依赖项** → 最终清单内部自相矛盾。
5. **把“暂定建议”写成“已确认”** → 假设冒充共识，后续返工。
6. **问自己能查到的事实** → 浪费用户注意力。

## 提问规则

### 1. 按依赖层级批量提问

先画出决策树，再按“上游决定下游”的顺序分批，每批通常 3–6 个问题；方案简单时可以更少，不为了凑数拆问题。

- 同一批尽量放置处于同一层、彼此可并行判断的决策点。
- 下游问题依赖上游答案时，先给上游问题；如果为了展示完整方案必须提前列出，要明确标注“以第 N 项建议为前提”。
- 每批末尾提供低摩擦回复方式：`全部采纳`、`只改第 N 项：...`、`其余采纳 / 我再补充`。

### 2. 每个问题都给出推荐答案

每个问题必须包含：

- **2–4 个具体选项**，每个选项说明收益、代价或风险；始终保留“其他 / 我自己说”。
- **一个明确推荐项**，不能只写“都可以”或“看情况”。
- **推荐依据**：来自代码、文档、现有规范、项目约束，或明确标注为经验判断。
- **影响范围**：该选择会改变哪些模块、流程、成本或后续决策。
- **置信度与风险**：高 / 中 / 低。低置信度时说明还需要什么证据。

没有足够信息形成推荐时，不要编造答案；把它标为“开放项”，并写明需要谁提供什么信息。

推荐优先级按以下顺序判断：

1. 满足已确认的业务目标和硬约束。
2. 不破坏现有架构、接口和业务边界。
3. 优先可逆、可验证、影响面小的方案。
4. 与项目已有规范和技术基线一致。
5. 在“足够好”时停止，不为理论最优增加无关复杂度。

### 3. 默认采纳建议，但保持“待确认”状态

问题批量给出后，Agent 可以把推荐项作为**暂定工作决策**继续分析，不再逐题等待确认。

- 用户逐项修正时，以用户答案覆盖建议。
- 用户说“全部采纳”时，可以作为最终建议列表输入，但仍要等最终列表被明确确认。
- 在最终清单里，未经明确确认的条目状态统一写为 `建议采纳（待确认）`，不得写成“已定”。
- 用户没有回复某条建议，不等于确认。

### 4. 先取证，再提问

问题涉及代码、文件、配置、依赖、目录结构时，先自行读取、搜索和核对。只把两类问题留给用户：

- **不可得事实**：业务意图、外部承诺、未来规划、组织约束。
- **价值判断**：取舍、优先级、风险容忍度。

能查到的事实直接写成“已确认事实”，不再作为问题。

### 5. 采纳修正后，向下传播影响

用户修正任一建议时：

1. 更新该决策点。
2. 找出所有依赖它的下游问题和建议。
3. 重算受影响项；必要时替换建议、补充新问题或标为开放项。
4. 在下一版清单中明确标出“本次修改”和“受连带影响”的条目。
5. 未受影响的建议继续保留，不重新拷问全部内容。

### 6. 最终确认是唯一关门条件

只有用户对完整建议列表明确回复“确认”“采纳”“可以”等同意表达后，才能输出“已确认决策”。

用户可以：

- 直接确认整份列表；
- 按编号修正：`第 2 项改为 B，第 5 项保留建议，其余采纳`；
- 新增约束或推翻已有建议。

收到修正后先更新建议列表并说明连带变化，再等待确认。连续修正时保持同一份主清单，不散落成多份无法追踪的结论。

## 流程

1. **听完整描述**：复述目标、边界和当前已知事实（1–2 句）。
2. **自己探查**：读取相关代码和文档，排除事实类问题。
3. **构建决策树**：列出关键决策点、依赖关系、影响面和优先级。
4. **分批提问并给建议**：每批 3–6 个，逐项给出选项、推荐、依据、代价和风险。
5. **暂定采纳**：把推荐项作为 `建议采纳（待确认）` 继续推演；合并用户已给出的修正。
6. **输出最终建议列表**：覆盖所有关键决策、开放项和连带风险，请用户一次性确认或按编号修正。
7. **处理反馈**：用户修正后更新主清单、重算依赖项并再次提交确认；用户确认后再标记为“已确认”。

如果用户中途叫停：停止扩展问题，输出当前建议列表、开放项和尚未覆盖的分支。

## 批量提问格式

```markdown
## 第 1 批问题（上游决策）

1. <决策点>
   - A. <选项>（收益 / 代价）
   - B. <选项>（收益 / 代价）
   - C. <选项>（收益 / 代价）
   - 建议：B
   - 依据：<代码 / 文档 / 约束 / 经验判断>
   - 影响：<会改变什么>
   - 置信度：<高 / 中 / 低>；风险：<一句话>

2. <决策点>
   ...

请回复：`全部采纳`，或 `第 2 项改为 A，其余采纳`。
```

## 最终建议列表格式

```markdown
## 建议列表（待确认）

| # | 决策点 | 建议结论 | 依据 | 替代项与代价 | 风险 / 开放项 | 状态 |
|---|--------|----------|------|--------------|---------------|------|
| 1 | <决策点> | <建议> | <依据> | <备选> | <风险> | 建议采纳（待确认） |
| 2 | <决策点> | <建议> | <依据> | <备选> | <风险> | 建议采纳（待确认） |

### 开放项

- <决策点>：<缺什么信息，谁能提供，影响哪些条目>

### 确认方式

- 全部确认：回复 `确认`
- 局部修正：回复 `第 2 项改为 <答案>，其余采纳`
```

用户确认后，再输出：

```markdown
## 已确认决策

- <决策点>：<最终结论>（依据：<一句话>）
```

清单中不得混入对话里没有形成、也没有列入推荐并经用户确认的内容。

## 纪律边界

- 追问 ≠ 审问。语气是“我已经替你收敛了一版，你只需纠错”，不是“证明你错了”。
- 不为了凑批量而问低价值问题；只问会改变范围、架构、接口、数据、流程、成本或风险的事项。
- 用户已明确决策的，直接写入清单，不再反复挑战。
- 推荐错误由用户修正；用户修正后以用户结论为准，不争辩。
- 追问和确认过程中**不要动任何文件、不要开始实现**。确认的是决策列表，不等于授权执行后续实现。
