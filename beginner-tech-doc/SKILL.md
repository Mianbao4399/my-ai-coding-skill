# 新手友好技术文档生成（Beginner Tech Doc）

用户提出技术知识类问题时：**先搜索验证，再按固定结构生成文档**。目标——开发新手看完就能独立走完全流程，不在任何一步卡住。

## 工作流（严格按序）

1. **确认范围**：问题过大时先问一次用户（用 AskUserQuestion 出 2~4 个带推荐答案的选择题，一次问清主题边界、输出路径；受众固定为零基础小白，不必询问）；已明确则直接进行。
2. **搜索验证**（必须，不可跳过）：
   - 注意：WebSearch / WebFetch 在 Trae 中是延迟工具，先用 ToolSearch 加载其 schema，再经 DeferExecuteTool 调用；调用格式是 `DeferExecuteTool({ toolName: "WebSearch", params: { query: "..." } })`——必须用 toolName + params 双层包装，不要把搜索参数直接展开传入；
   - 用 WebSearch / WebFetch 核实**易过时或易错的信息**：版本号、政策/审核规则、价格/配额、界面菜单路径、错误码、命令参数、官方文档；
   - 稳定的底层原理可依赖模型知识，但文中**每一条"当前事实"（如"Xcode 14 起移除 Bitcode"）必须有搜索依据**；
   - 搜索至少覆盖：官方文档/权威来源 1 个 + 中文实践来源 1 个；结论冲突时以官方为准，落笔只写正确结论，核验过程不写进正文；
   - 搜索返回的摘要（snippet）只用于定位线索，不同来源的摘要常互相矛盾：凡写入文档的版本号、数字、时间线，必须用 WebFetch 打开官方原文核实后才算验证通过；
   - 在文档中标注信息核验日期。
3. **按模板生成文档**：结构见 `assets/doc-template.md`，先读它再动笔。
4. **保存**：默认存到当前工作区根目录，用户指定路径（如 Downloads）则照办；文件名 `<主题>知识体系.md` 或 `<主题>新手实战.md`。
5. **卡点自检**：交付前逐条过下面的自检清单，不达标就补写。

## 增量更新模式（用户要求补充或更新已有文档时）

不走"重新生成"，按更新流程：

1. **先读全文**：读完整份目标文档，掌握章节编号、目录与交叉引用结构；
2. **判断动作**：新增章节 / 扩写既有小节 / 修正错误，三者取其一或组合；
3. **编号纪律**：优先把新内容以"小节"形式并入主题最相近的既有章节（学习顺序与编号稳定两全）；确需独立成章且插在中间、导致后续章节顺延时，**全文交叉引用同步重编号**；追加为新末章或附录是最后的选择；
4. **收尾同步**：更新目录清单、刷新文档头部的信息核验日期；
5. **重跑卡点自检清单**，特别是编号与交叉引用一项。

## 文档内容规则（从多轮实战中沉淀）

- **受众定义（写死）**：新手一律指零基础小白——不假设读者具备任何领域前置经验，相邻领域的常识性概念（如给 iOS 开发者讲 RN 时出现的 deployment target）首次出现也要中英对照 + 大白话；解释宁多勿少。
- **反 AI 味（硬性）**：交付前逐段自查四类痕迹——模板化排比（连续多个"**标签**：解释"结构）、关键词堆砌的名词串、自我声明式标题（如"真实事故现场（都来自实际项目）"）、考据型元叙述（如"原始材料说……""很多旧教程都写错了""这里有一条重要纠正"）——发现即改为叙述式表达。
- **正文不写考据**：文档只呈现结论、原理、操作与排障，不写"本文基于哪些材料""原始材料怎么说""哪些资料写错了"，不设"勘误"附录。事实冲突在核验阶段解决；确需提醒读者避免旧做法时，用一句客观事实对比（如"iOS 17.4 起支持；EEA 之外不可用"），不评价资料来源。
- **代码篇幅红线**：文档收录"最小可懂片段"，不当代码收纳册。单个代码块不超过 30 行；完整工程与运行示例放代码仓库，文档里只留运行说明；全文代码总量不超过正文的四分之一。
- **比喻开路**：文档开头用一张"概念 ↔ 日常比喻 ↔ 一句话职责"表格建立全局直觉，收尾一句串联主线。
- **概念三段式**：每个概念按"是什么（带比喻）→ 为什么需要 → 怎么用/排查"展开；**专业名词首次出现必须中英对照 + 一句大白话解释**（如 非对称加密 Asymmetric Cryptography——"私钥是章，公钥是章印比对样本"）。
- **操作必写入口**：每个实操步骤写明"在哪个界面点哪个按钮/哪条命令"，命令逐个 flag 加注释；图形操作用 `A → B → C` 菜单路径写法；标注新旧版本菜单名差异。
- **报错三件套**：现象（报错原文代码块）→ 原理（新手版大白话）→ 解法（按推荐顺序编号），有就加"预防"。与自然文风共存的方式：现象和原理用自然段落叙述（允许口语化），解法与预防用固定标记行（如"**怎么办**：""**预防**："）单独拎出，保证扫读性。
- **速查表优先**：错误码、类型对比、配置字段等信息用表格；可截图对号入座的（如"装机校验 5 步"）写成清单。
- **全景 SOP**：单独一节给"从零到完成"的按序步骤线（第 0 步→第 N 步），每步链接回知识章节；**前置条件（账号/费用/资质）必须作为第 0 步写明**——新手常卡在"还没开始动手的准备工作"。
- **动态信息防御**：政策、价格、审核规则等会变的内容写"以官方页面为准"并给出官方链接。旧机制只在仍会影响读者决策时用一句事实对比说明，不写"旧教程如何说"。
- **交叉引用**：文内用章节编号互链；外部引用写明来源。
- **语言**：正文中文；精简、关键词导向，不写空话套话，也不写与读者任务无关的写作过程说明。

## 卡点自检清单（全部达标才交付）

- [ ] 新手按 SOP 从第 0 步走到底，每一步都知道"在哪操作"？
- [ ] 每个可能失败的步骤都有报错现象 + 解法？
- [ ] 每个专业名词首次出现有中英文 + 大白话？
- [ ] 逐段过了"AI 味"自查（无模板化排比 / 堆砌名词串 / 自我声明式标题），文风自然且解法仍可扫读？
- [ ] 正文没有考据/勘误/材料对比等元叙述，也没有"旧认知""重要纠正"式标题？
- [ ] 代码是"最小可懂片段"（单块不超过 30 行、总量不超正文 1/4），完整示例指向代码仓库？
- [ ] 所有"当前事实"（版本/政策/价格/菜单路径）经过搜索验证并注明核验日期？
- [ ] 前置条件（账号、费用、资质、环境）没有遗漏？
- [ ] 动态信息有官方链接兜底？
- [ ] 增量更新后章节编号连续、交叉引用指向真实存在的章节？
- [ ] 有全景 checklist 可供收藏执行？

## 边界

- 简单事实问答、本地代码编写/调试、纯代码实现任务不触发本技能的完整流程，正常回答即可。
- 用户只要"简短回答"时不要强行输出文档。
- 搜索无法核实且缺乏权威来源的内容，在文中明确标注"未经验证"，不要冒充事实。
