## 0. 先用一组比喻建立全局

| 技术概念 | 英文 | 比喻 | 一句话职责 |
|---|---|---|---|
| 智能体 | Agent | 会自己动手干活的助理 | 接任务、拆步骤、调工具、给结果 |
| 核心循环 | Agent Loop | 助理的"想—做—看—再想"工作习惯 | 推理与工具调用反复交替直到完成 |
| 工具 | Tool | 助理手里的业务窗口 | 每个 API 对 Agent 来说就是一个工具 |
| 工具调用 | Function Calling / Tool Calls | 助理填单子去窗口办事 | 模型输出"要调哪个工具+参数" |
| 上下文 | Context | 助理的工作记忆 | 模型一次能看到的所有对话内容 |
| 流式输出 | Streaming | 打字机一样一段段蹦字 | 用户不用干等完整回答 |
| 服务器发送事件 | SSE（Server-Sent Events） | 广播电台单向播报 | 服务端向 App 持续推送消息 |
| 长连接 | WebSocket | 打通的双向对讲机 | App 和服务端随时互发消息 |
| 结构化卡片 | Card Message | 聊天里的"图文卡片" | 故障记录、配件商品用卡片渲染 |
| 检索增强生成 | RAG（Retrieval-Augmented Generation） | 先查资料再回答 | 知识库按语义搜出相关内容喂给模型 |
| 危险操作确认 | Human-in-the-loop | 大额转账前再看一眼 | 下单等写操作必须用户点头 |
| 车辆上下文注入 | Vehicle Context Injection | 助理桌上常备的客户档案 | 会话绑定车辆，模型自动知道在说哪台车 |
| 令牌 | Token | 模型计费的"字数" | 输入输出按 token 计量与计费 |

串起来就是一句话：**App 负责把话说好把卡画好，Agent 服务负责"想"和"调度"，业务 API 负责"真正干活"——中间靠一套结构化消息协议和工具约定把三方焊在一起。**

## 一、项目定位：要做一个什么东西

在车务 App（Flutter 跨端）里加一个 AI 助手聊天窗口。用户用自然语言提问，助手自主完成三件事的串联：

1. **查**：调 OBD 平台接口，拉取车辆故障码与故障记录；
2. **讲**：查汽车故障知识库，给出故障原因、严重程度、维修建议；
3. **办**：查配件商城找到适配配件，用户确认后下单购买。

一条典型对话："我的车最近提示发动机故障，怎么回事？"——助手查到 P0420 故障码，解读含义与风险，列出适配 VIN 的配件并附价格，用户点击卡片完成购买。**一次对话串起三个业务系统，这是本项目的核心价值，也是它和普通客服机器人 chatbot 的本质区别**：chatbot 只会说话，Agent 会动手。

明确的边界：本项目**不做**自动诊断（诊断逻辑仍在 OBD 盒子与平台侧）、**不做**无人干预的自动下单、**不做**通用闲聊助手。

## 二、总体架构：三端分工

```
┌─────────────────┐  WebSocket 双向长连接   ┌───────────────────────────┐
│  App 聊天窗口    │ ◄────────────────────► │  Agent 服务（新增，Python） │
│  （Flutter）     │   结构化 JSON 消息       │                           │
└─────────────────┘                        │  核心循环（推理+工具调度）   │
                                           │  上下文管理 / 会话持久化     │
                                           └──────┬──────┬──────┬──────┘
                                                  │      │      │
                                              工具①    工具②   工具③
                                             OBD 故障  故障知识  配件商城
                                             记录 API  库 API    API
                                           （三个都是已有业务接口，Agent 只封装不改造）
                                                  │
                                             ┌────▼────┐
                                             │ LLM API │  DeepSeek（OpenAI 兼容格式）
                                             └─────────┘  provider 抽象层可切换
```

| 层 | 职责 | 明确不做的事 |
|---|---|---|
| App 聊天窗口（Flutter） | 收发消息、流式渲染、卡片 UI、下单确认弹窗、断线重连 | 不碰 LLM、不拼提示词、不直调业务 API |
| Agent 服务（新增后端） | 核心循环、工具调度、上下文与会话管理、消息协议实现 | 不写业务逻辑，业务逻辑留在原有 API 里 |
| 业务 API（已有） | OBD / 知识库 / 商城各自的接口与数据 | 不感知 Agent 存在，原样复用 |

**Agent 服务是独立新增的微服务**，不是塞进现有后端的模块。它只依赖三个已有 API 的服务端接口，未来加新能力（比如保养预约）就是加一个工具，App 端只需加一种卡片渲染。

## 三、消息协议：App 与 Agent 服务之间的普通话

App 和 Agent 服务之间走 WebSocket（或 SSE）长连接，消息一律是结构化 JSON。这是三端协作的"合同"，**协议先行，三个领域并行开发的分歧点都由它裁决**。

| 消息类型 | 方向 | 作用 | App 渲染方式 |
|---|---|---|---|
| `text_delta` | 下行 | 流式文字片段，逐段下发 | 追加到当前气泡，打字机效果 |
| `tool_status` | 下行 | 工具调用过程提示 | 会话内灰色小字："正在查询故障记录…" |
| `card` | 下行 | 结构化卡片数据 | 按卡型渲染：故障记录卡 / 知识解读卡 / 配件商品卡 |
| `confirm` | 下行 | 危险操作确认请求 | 弹确认框，带 `confirmId` |
| `error` | 下行 | 出错告知 | 气泡内红字提示 + 重试按钮 |
| `user_message` | 上行 | 用户发言 + 车辆 ID + 会话 ID | — |
| `confirm_result` | 上行 | 用户对确认操作的答复 | — |

卡片消息示例（配件卡，含跳转商城的深链）：

```json
{
  "type": "card",
  "cardType": "part",
  "payload": {
    "partId": "P-88231",
    "name": "前氧传感器",
    "brand": "博世",
    "price": 285.0,
    "fitVin": "LSVAA1234E1234567",
    "buyUrl": "app://mall/part/P-88231"
  }
}
```

**卡片化是最重要的体验决策**：故障记录和配件列表如果用纯文本吐出来，排版不可控、按钮加不了。工具返回结构化数据后，Agent 服务把"给模型看的 JSON"和"给 App 渲染的 card 消息"分开下发——模型拿数据做推理，App 拿卡片画 UI，商品卡自带"去购买"按钮。

## 四、关键设计决策与理由

| # | 决策 | 理由 |
|---|---|---|
| 1 | 业务 API 工具化，Agent 只做薄封装 | 业务逻辑不动，接口复用；新增能力 = 新增工具，改动面最小 |
| 2 | 手写核心循环，不用 LangChain 等重框架 | 循环本身只有几十行；框架抽象层经常与 SDK 版本脱节，出问题难排查 |
| 3 | 原生 Tool Calls（function calling）协议 | DeepSeek 官方支持且带 `strict` 模式校验参数，稳定可靠 |
| 4 | LLM 走 provider 抽象层，以 DeepSeek 为例 | OpenAI SDK 兼容格式，换模型只改 `base_url` 和模型名，不锁定厂商 |
| 5 | 结构化卡片协议 | 给模型的数据和给 UI 的数据分离，双方各取所需 |
| 6 | 车辆上下文自动注入 | 会话创建时绑定车辆 ID 写入系统提示词，模型调工具自动带上，用户不用报车牌 |
| 7 | 鉴权透传 | Agent 服务代表用户调业务 API，携带用户 token，用户 A 永远查不到用户 B 的数据 |
| 8 | 下单等写操作强制人工确认 | 商城"创建订单"工具标记为危险工具，必须走 `confirm` 流程，模型无权静默下单 |
| 9 | 会话按 用户+车辆 维度持久化 | 支持"上次说的那个故障"这类跨会话指代 |
| 10 | 上下文超限走压缩摘要，不上向量库 | 一期方案最简单有效；向量检索留给知识库场景（见后端篇） |
| 11 | 数据与指令隔离 + 注入保守路径 | 工具返回按"数据"对待，其中的指令一律不执行；注入检测命中走保守路径（强制 confirm、收窄工具集），详见 Agent 篇安全与防注入章 |
| 12 | 长期记忆走"摘要提取写入 + 检索读回"，不引重型记忆组件 | 一期与上下文压缩共用摘要基建，读回 Top 3~5 条；数据量大后再考虑向量检索（见 Agent 篇记忆系统章） |

## 五、技术选型总表

| 领域 | 选型 | 版本核验（2026-11-27） | 选择理由 |
|---|---|---|---|
| App | Flutter + Dart | Flutter 3.50（2026-11-11 发布）+ Dart 3.14 | 跨端一套代码；流式聊天 UI 生态成熟 |
| Agent 服务 | Python + FastAPI | FastAPI 0.143+（2026-10 起） | 异步原生，WebSocket/SSE 支持好；AI 生态最全。Agent 服务属 I/O 密集型，语言本身开销毫秒级，不构成速度劣势（见 Agent 篇响应速度章） |
| LLM | DeepSeek（`deepseek-flash` / `deepseek-v4-pro`） | 官方文档核验 | OpenAI SDK 兼容、Tool Calls 与 JSON Output 支持、国内直连、价格见官方页 |
| 实时通信 | WebSocket（App↔Agent 服务），服务间 HTTP | — | 双向推送 tool_status 与卡片需要长连接 |
| LLM SDK | `openai` Python SDK 指向 DeepSeek base_url | — | 官方推荐的接入方式，流式与工具调用开箱即用 |
| 参数校验 | pydantic | — | 工具参数声明即 schema，与 Tool Calls 的 JSON Schema 天然同源 |

备选说明：若后续需要切换通义千问 / GLM / OpenAI，只需在抽象层新增一个 provider 配置（各家均兼容 OpenAI 格式或提供适配），业务代码不动。

## 六、里程碑与任务分解（执行线）

> 本节是"执行线"，前面章节是"知识点"。里程碑按**完成标志**判定，不按日历时间。每个里程碑末尾附可演示场景——跑通 demo 比写完代码更重要。

### M1：单工具闭环（先跑通最小 Agent）

**目标**：Agent 服务 + 一个工具（OBD 故障记录）+ 一个临时测试页面，端到端跑通"问一句 → 调工具 → 回答"。

| 领域 | 任务 |
|---|---|
| Agent 服务 | 项目骨架（FastAPI + uvicorn）；DeepSeek 抽象层（base_url + API key）；核心循环 v1（轮数上限 + 错误回喂）；OBD 工具封装（读接口 + pydantic schema）；本地命令行入口 |
| 后端配合 | 提供 OBD 测试环境接口文档与测试账号；约定服务间鉴权方式 |
| 前端 | 暂不参与（Agent 服务用命令行/HTTP 调试页自测） |

**完成标志**：命令行输入"我的车有什么故障？"，Agent 调用 OBD 测试接口并正确口头总结故障码。全程无人工干预，工具报错能自我修正。

### M2：三工具 + 消息协议 + App 接入

**目标**：协议定稿，三工具齐活，Flutter 聊天窗口接入并渲染卡片。

| 领域 | 任务 |
|---|---|
| 三端共同 | 消息协议 v1 定稿（七种消息类型 + 三种卡片 schema），评审后冻结 |
| Agent 服务 | WebSocket 端点 + 会话管理；知识库工具（故障码精确查询 + 症状 RAG 检索）；商城工具 v1（搜索配件）；卡片消息下发；tool_status 下发 |
| 后端配合 | 知识库检索接口（含 RAG）联调；商城搜索接口联调 |
| 前端 | WebSocket 接入 + 断线重连；text_delta 流式气泡；三种卡片 Widget；tool_status 展示 |

**完成标志**：真机演示本文第一章的典型对话——查故障 → 解读 → 出配件卡片，卡片可点击跳转商城。

### M3：交易闭环与体验完善

**目标**：能安全地下单，体验达到可灰度水平。

| 领域 | 任务 |
|---|---|
| Agent 服务 | 商城"创建订单"危险工具 + confirm 确认流程；会话持久化（用户+车辆维度）；上下文压缩（超 70% 窗口触发摘要）；限流重试与费用埋点 |
| 后端配合 | 下单接口联调（含幂等与回调）；用户 token 校验对接 |
| 前端 | confirm 弹窗与 confirm_result 上行；错误消息展示与重试；弱网体验（消息缓冲、加载态） |

**完成标志**：对话内完成"推荐配件 → 确认 → 下单成功"全流程；断网重连后对话不丢；连续多轮对话不炸上下文。

### M4：进阶增强（按需排期）

| 领域 | 任务 |
|---|---|
| Agent 服务 | 子 Agent 拆解复杂任务；工具调用链路观测（日志 + 耗时埋点）；prompt 迭代机制（版本化 + 回归用例） |
| 后端配合 | 知识库 embedding 质量优化（坏例集评测）；商城比价接口（多商家） |
| 前端 | 消息内图片/文档渲染；主动提醒推送（新故障码触达） |

**完成标志**：按业务优先级逐项验收，不设统一标志。

## 七、协作约定与联调顺序

**协议冻结原则**：M2 开始前，消息协议和三种卡片 schema 必须三端评审冻结。之后字段只增不改，改名等于破坏契约。

**联调顺序**（依赖决定顺序，不可乱）：

1. Agent 服务先用 mock 数据自测核心循环（不等任何人）；
2. 后端给 OBD 测试接口 → Agent 服务接入真数据（M1 依赖）；
3. 三端评审协议 → 冻结 → Flutter 联调 Agent 服务（M2 依赖）；
4. 知识库、商城接口按工具逐个接入（M2 内并行）；
5. 下单链路最后联调（涉及资金，放 M3 并要求测试环境隔离）。

**环境约定**：DeepSeek API key、业务测试环境地址全部走环境变量或配置文件，任何密钥不进代码仓库。

## 八、风险清单与对策

| 风险 | 场景 | 对策 |
|---|---|---|
| 模型幻觉 | 编造不存在的故障码解释、虚构配件 | 知识库答案要求"给出处"；配件只用工具返回的真实数据；prompt 明确"查不到就说查不到" |
| 误下单 | 模型解析歧义导致错误下单 | 下单必走 confirm；订单创建接口加幂等键；金额上限风控 |
| 上下文超限 | 长对话 + 大工具结果撑爆窗口 | 工具结果截断摘要后再入上下文；压缩机制；DeepSeek 上下文 1M 但费用随长度增长，要有预算意识 |
| 费用失控 | 循环失控反复调工具 | 最大轮数上限；单会话 token 预算；按 peak/off-peak 时段计费差异做调度（见官方价格页） |
| 接口变更 | 业务 API 改字段打爆工具 | 工具封装层做 schema 校验，字段变更在封装层报警而不是让模型拿到脏数据 |
| 数据越权 | 用户 A 查到用户 B 的故障记录 | 鉴权透传 + 后端接口按用户隔离，Agent 服务不自行实现权限逻辑 |
| 响应偏慢 | 用户觉得 AI 回复慢、干等没反馈 | 流式必开；简单轮次关思考模式；减少工具轮数；上下文压缩——速度与费用同源，详见 Agent 篇响应速度章 |
| 提示词注入 | 恶意用户或被投毒的知识/商品数据诱导 Agent 越权 | 权限最小化（能力=工具清单）+ 数据指令隔离 + 注入检测信号，详见 Agent 篇安全与防注入章 |
| 提示词泄露 | 系统提示词被用户套取 | 敏感逻辑只放代码；套取类请求固定应答；出口过滤——目标是泄露了也不致命 |
| 跨会话指代失效 | 用户回来问"上次那个配件买了没"，Agent 读不到历史 | 会话持久化 + 长期记忆读回（Top 3~5 注入工作记忆），详见 Agent 篇记忆系统章 |

**排障"动手顺序"速查**（任何"Agent 不对劲"先走这张）：

```
① 先看 Agent 服务日志：是模型没调工具、工具报错、还是流式中断？
② 用 curl 直接调涉事业务 API：接口本身好坏一眼定性
③ 用最小脚本直连 DeepSeek API：排除 SDK/网络因素
④ 检查消息协议：App 收到的原始 JSON 是否符合 schema
⑤ 最后才动 prompt：前三步没定位前，改 prompt 只会引入新变量
```
