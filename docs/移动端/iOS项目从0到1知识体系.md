## 第 0 章 先用一组比喻建立全局

| 技术概念 | 英文 | 比喻 | 一句话职责 |
|---|---|---|---|
| MVP | Minimum Viable Product（最小可行产品） | 只卖招牌菜的新店首月 | 用最小功能集验证"有人愿意用"，再决定加菜 |
| AI Agent | AI 智能体 | 7×24 在线、懂车的 AI 咨询师 | 用大模型+工具替用户完成问诊对话 |
| 流式输出 | Streaming | 打字机效果 | AI 回复边生成边显示，用户不用干等 |
| 技术选型 | Technology Selection | 装修前定水电走向 | 决定日后改动的成本，错一次伤半年 |
| 需求排期 | Roadmap / Scheduling | 装修工期表 | 把有限的人力排进能对外承诺的时间 |
| 灰度发布 | Staged Rollout | 新菜先给熟客试吃 | 新版本先放给一小部分用户，出事影响面小 |
| D-U-N-S 编码 | Data Universal Numbering System | 公司的全球"身份证号" | 注册苹果公司开发者账号的必需材料 |
| App 备案 | — | 开店前办营业执照 | 国内 App 分发的法定前置手续 |
| 软著 | 计算机软件著作权证书 | 软件的"出生证明" | 国内安卓应用商店上架必备资质 |
| IAP | In-App Purchase（应用内购买） | 商场统一收银台 | 苹果代收数字商品款项并抽成的机制 |
| IM SDK | Instant Messaging SDK | 请专业队装好电话系统 | 聊天能力不必从零自研 |
| APNs | Apple Push Notification service | 苹果官方传呼台 | iOS 推送的唯一官方通道 |
| OBD | On-Board Diagnostics（车载自动诊断） | 汽车的体检接口 | 车上读取故障码的标准插座 |
| BLE | Bluetooth Low Energy（低功耗蓝牙） | 省电的短对讲机 | 手机与 OBD 盒子之间的通信方式 |
| CI/CD | Continuous Integration / Delivery | 自动打包流水线 | 让"编译—测试—分发"不再靠人肉 |
| ADR | Architecture Decision Record（架构决策记录） | 重大决定的会议纪要 | 半年后还记得"当初为什么这么选" |

一条主线把全篇串起来：**先把边界（钱、人、时间、资质）问清楚 → 圈定最小业务闭环 → 打地基（选型、账号、备案、基建） → 双周小步迭代 → 提审上架 → 用数据决定下一道菜。**

## 第一章 入职后的行动顺序（先做什么，再做什么）

### 1.1 第 1 周：问清六个边界问题（一行代码都不用写）

技术选型的所有答案，都藏在这六个问题的答案里。这一周的任务是把它们全部问实。

| # | 要问清的事 | 为什么先问 | 直接影响哪个决策 |
|---|---|---|---|
| 1 | 预算与人数（能给几个人、多少钱） | 决定走跨端还是双原生 | 第四章 |
| 2 | 有没有硬死线（展会/融资/招商会） | 决定 MVP 砍到多小 | 第五章 |
| 3 | 双端范围：iOS+安卓都要？小程序要不要？ | 决定技术路线与备案工作量 | 第四章 |
| 4 | 商业模式：谁付钱（车主/会员/商城毛利） | 决定苹果支付路线（见第六章收钱判断表） | 第六章 |
| 5 | 维修执行谁来落地（用户自装 / 合作修理厂送修） | 没有门店时，它决定商城卖什么、业务闭环到哪一步收口 | 1.2 闭环图 |
| 6 | 公司资质现状（营业执照、域名、服务器、已有账号） | 备案与签约都要主体资质，晚一天项目晚一天 | 第六章 |

> **新手常见疑问：我是技术负责人，为什么第一周不写代码？**
> 因为从 0 到 1 的项目里，**最慢的从来不是写代码，而是手续**：苹果公司账号要 D-U-N-S（免费，但常要等 1~2 周）、软著要版权中心审核、备案要管局审核。第 1 周不递材料，第 12 周你开发完了却没地方上架。

### 1.2 第 1~2 周：画出业务闭环，圈定 MVP

把公司的设想变成一张图。按你给定的业务形态（AI Agent 问诊 + OBD 盒子数据，暂无门店与技师），业务闭环长这样：

```
车主发现故障（仪表灯亮 / 异响 / OBD 报故障码）
        │  ① 拍照 + 描述症状（OBD 盒子若已接入，自动带上故障数据）
        ▼
   AI 问诊对话（WebSocket 流式回复；AI 读图辅助判断）
        │  ② AI 给出原因判断 + 维修建议 + 配件推荐卡片
        ▼
   商城下单（配件/耗材，自营 SKU）
        │  ③ 微信 / 支付宝支付
        ▼
   配件物流 → 用户自装 / 送修（维修执行环节由业务确认，见 1.1 第 5 问）
        │  ④ 评价、追问、复购
        └────────────→ 回到"车主发现故障"
```

**这张图的作用**：v1.0 只需要让 ①→③ 跑通，④ 往后都是迭代。凡是闭环之外的"好点子"，先记进需求池，不进排期。

紧接着做五个关键决策，每个都影响一个季度的工作量：

| 决策点 | 选项 | 建议 |
|---|---|---|
| AI 读图 | v1.0 要 / 不要 | **要（P0）**：拍仪表盘/故障部位照片是车主最自然的表达方式，读图能力已成熟 |
| AI 读视频 | 要 / 不要 | 先不做（你的判断正确）：抽帧上传+多图消息成本高、响应慢，放 P2 |
| OBD 盒子形态 | 自带网络直报云端 / 仅蓝牙由 App 转发 | 找硬件负责人确认（见 7.8）；两种形态都不阻塞 AI 问诊主链路 |
| 真人客服 | v1.0 要 / 不要 | 放 P1：先用 AI 兜底，加"转人工"入口时再接云 IM 客服模块 |
| 商城规模 | 自营少量 SKU / 第三方商家入驻 | v1.0 只做自营配件 SKU；第三方入驻涉及平台资质，先过法务 |

### 1.3 与写代码并行：启动"慢手续"

上面说过，手续是最长的等待项。第 1~2 周内，下面这张表里的每一项都要**递出去**：

| 手续 | 办理入口 | 大致节奏 | 费用 | 卡点提示 |
|---|---|---|---|---|
| D-U-N-S 编码 | Apple 官网免费申请页 | 1~2 周（部分可加急） | 免费（苹果官方明确不收费） | 公司开发者账号的前置材料 |
| Apple Developer Program 公司账号 | developer.apple.com → Programs → 注册 | 材料齐后数天 | ¥688/年（官方中文页标价） | 一定用公司主体，别用个人账号 |
| 各安卓商店开发者账号 | 华为/小米/OPPO/vivo/荣耀等开发者平台 | 逐家 1 天~2 周 | 以各平台公示为准 | 需营业执照；上架时需软著（见第六章） |
| 软件著作权 | 中国版权保护中心，或找代理 | 官方流程数周，代理可加急 | 数百到千元级 | 安卓上架硬材料，最晚第 2 周递 |
| 域名 ICP 备案 | 服务器所在云厂商的备案系统 | 1~3 周 | 免费 | 服务器需在国内 |
| App 备案 | 由接入服务商/分发平台代提交，最终在工信部系统确认 | 与 ICP 备案联动 | 免费 | 2024 年 4 月起未备案的 App 不得分发（见第六章） |
| 微信开放平台/移动应用 | open.weixin.qq.com | 审核约 1~7 天 | 开放平台免费（支付商户号另行签约） | 需营业执照与对公账户 |
| 支付宝开放平台 | open.alipay.com | 类似 | 类似 | 同上 |
| 隐私政策与用户协议 | 法务或外部律师 | 与备案同步 | — | 所有商店都要求可访问的在线链接 |

费用小结给老板报预算用：固定支出很低——苹果账号 ¥688/年、软著官费 0（代理加急另算）、两道备案 0、安卓商店账号多数免费；真正按量花钱的是云上服务（IM/推送/短信/一键登录按次或套餐）。**钱的大头在人力，不在手续。**

### 1.4 第 2~3 周：选型定稿、组队、打地基

三件事并行：

1. **技术选型定稿**：用第二章到第四章的结论，写成一页 ADR（见 8.6 节模板），拉着后端负责人一起签认——选型是双向约束，客户端定 Flutter 就意味着后端联调节奏也定了。
2. **组队**：最小配置见 8.7 节。招聘面试题里放一道"给你一个聊天页 + 一个商品详情页，说说你怎么搭"这种贴合业务的题。
3. **基建**：Git 仓库、CI 流水线、三方服务开通（第七章的清单一次开齐），标准是"任何人 clone 完仓库，一条命令能在模拟器跑起来"。

### 1.5 第 4 周起：双周迭代

进入第五章的排期节奏。行动顺序一句话版：**第一周问边界、递材料；第二周画闭环、定 MVP；第三周定选型、搭基建；第四周开始双周迭代。**

### 1.6 谁做什么：已有盘点、分工矩阵与跨部门沟通

#### 已经有了什么（先盘点，别重复采购）

公司已有网站，左表这些大概率已有——先逐项核实再动手；右表是大概率要新办的：

| 大概率已有 | 核实要点 |
|---|---|
| 营业执照、对公账户 | 备案与支付签约都用它 |
| 域名 | 域名实名主体是否在公司名下 |
| 网站 ICP 备案 | 备案主体与营业执照一致？是否处于有效状态（未被注销）？ |
| 云服务器与云账号 | 服务器在国内哪家云厂商——App 备案要走这家接入商的流程 |
| 微信公众号/支付商户号（可能有） | 公众号≠开放平台移动应用，App 支付要另建移动应用条目 |

| 大概率没有、必须新办 | 说明 |
|---|---|
| 苹果公司开发者账号 + D-U-N-S | iOS 负责人发起 |

| 事项 | 主责 | 配合 | 备注 |
|---|---|---|---|
| D-U-N-S 编码 + 苹果公司账号 | **iOS 负责人（你）** | 行政（营业执照、法人信息） | 见 1.3 |

#### 跨部门沟通怎么做（可直接照抄的节奏）

1. **入职第一周开一次 30 分钟"资质启动会"**：把分工矩阵投在屏幕上，当场认领、当场定截止日期——会后这张表就是唯一事实源，不靠口头约定。
2. **建一张共享进度表**：每行一个手续，列＝主责/协作/状态（未启动/材料已递/审核中/完成+回执号）/截止日。每周五各主责更新一次。
3. **材料一次性要齐**：给法务和行政的邮件里直接附"所需材料清单"（营业执照副本扫描件、法人身份信息、对公账户信息、公章用印申请、公司邮箱），一次要全，不要挤牙膏式反复要。
4. **法务意见要落文字**：口头"可以"不算数，要求邮件回复结论并归档进选型 ADR 附录——半年后出争议这就是依据。
5. **给老板的节奏**：每两周发一页纸——手续进度红绿灯 + 开发里程碑 + 阻塞项。有阻塞（D-U-N-S 卡住、软著代理拖延）当天上报，别攒到双周报。
6. **与安卓负责人的接口**：共用一张"双端对齐表"——登录/支付/推送 SDK 选型两端统一、消息协议版本号一致（仓库《车务Agent项目总览与路线图》已冻结七种消息协议）、发版节拍对齐（同周提审）。

## 第二章 技术选型① 语言——OC 还是 Swift

### 2.1 是什么

- **Swift**：苹果 2014 年发布、官方主推的开发语言，相当于苹果生态的"普通话"。Xcode 26 搭载的是 Swift 6.2（信息核验日期见文档头）。
- **Objective-C（OC）**：更老的一门语言，iOS 早期十几年都用它写，相当于"老方言"。大量底层框架至今仍由 OC 编写，苹果仍在维护它的工具链。
- **Swift Concurrency（Swift 并发）**：Swift 的 async/await 语法，大白话是"写起来像一步一步排队，实际底层自动帮你切换线程"，处理网络请求这类耗时操作时不容易写出死锁和回调地狱。

### 2.2 为什么新项目没理由选 OC 当主力

| 维度 | Swift | Objective-C |
|---|---|---|
| 官方态度 | 新特性、新框架示例都围绕 Swift（SwiftUI 对 Swift 支持最顺） | 维护状态，无新特性 |
| 写代码体验 | 类型检查严格，很多错误**编译期**就拦下；代码量明显更少 | 运行时才暴露的错多；写法啰嗦 |
| 新人上手 | 语法现代，前端/后端背景的人转得快 | 手动内存管理痕迹多，易踩坑 |
| 招聘市场 | 国内主流新项目都是 Swift，供给充足 | 岗位逐年减少，多为维护老项目 |
| 与老代码混编 | 桥接头（Bridging Header）一行配置即可共存 | — |
| 适合场景 | 一切新项目 | 维护多年老项目、对接只提供 OC/C++ 接口的底层库 |

一句话：**OC 不是不能用，而是"新写的每一行都要为它付出未来的维护成本"。你们没有历史包袱，就没有理由背这个包袱。**

### 2.3 什么时候还会碰到 OC

- 某个老的三方库只提供 OC 接口：用桥接头接进 Swift 工程即可。
- 对接 C/C++ 底层库（如某些音视频、加密库）：OC 是 C 的超集，这时 OC 反而是最薄的桥。
- 这些场景叫"混编"，不需要你用 OC 写业务页面。

### 2.4 结论

**主力语言选 Swift，OC 只出现在"必须用的老库"边界上。** 把这条写进 ADR，并注明"新文件一律 Swift，评审时见到新 OC 文件就打回"。

## 第三章 技术选型② UI 框架——UIKit 还是 SwiftUI

### 3.1 是什么

- **SwiftUI**：声明式（Declarative，"你只说要什么，框架负责画出来"）UI 框架，2019 年推出。比喻：乐高说明书——你按说明书拼，形状自动成型。
- **UIKit**：命令式（Imperative，"你一步步指挥怎么画"）UI 框架，2008 年第一代 iPhone SDK 就有。比喻：木工全屋定制——哪里都要你亲手量、亲手钉。
- **Deployment Target（最低部署版本）**：你的 App 允许安装到的最老系统版本。设 iOS 16，就意味着 iOS 15 的手机装不了你。

### 3.2 2026 年的现状

- 苹果官方文档已把 SwiftUI 列在 UIKit 之前，新项目的默认推荐；Xcode 的实时预览（Preview）等效率工具也都为 SwiftUI 设计。
- 社区与各技术团队的共识也是"多数新项目以 SwiftUI 为主"；但**相机取景、复杂富文本编辑、精密手势链**这类深度定制场景，仍要落回 UIKit（例如 SwiftUI 没有内建的原生相机取景视图，需要桥接 UIKit 的能力）。
- 苹果提审侧：2026 年 4 月起上传需用 iOS 26 SDK 构建；2027 年 4 月起需 iOS 27 SDK 且最低目标版本为 iOS 15（官方"提交 App"页面，核验日期见文档头）。

### 3.3 对照你们 App 的三种界面

| 界面 | 复杂点 | 框架判断 |
|---|---|---|
| 问诊表单（选车型、传图、描述症状） | 常规表单 + 图片选择 | SwiftUI 直接写，效率最高 |
| AI 问诊聊天页 | 键盘联动、消息气泡列表、长列表性能、打字机渲染 | SwiftUI 能做，但键盘与输入框细节必要时用 UIKit 兜底 |
| 商城列表/详情 | 复杂瀑布流、促销标签 | SwiftUI 的瀑布流布局 + 部分自定义组件即可 |

### 3.4 建议

**SwiftUI 为主、UIKit 兜底的混合策略**：

- Deployment Target 建议 iOS 16 起（NavigationStack 等基础能力在 iOS 16 齐备）；团队激进一点可以 iOS 17（`@Observable` 状态管理更省事）。别设到 iOS 15——为了老机型把开发效率拖住不划算，国内主流用户的系统版本通常比苹果统计的更新。
- 比苹果要求更高没问题，比"目标用户里占比 <2% 的老机型"更妥协没必要。
- 遇到 iOS 17/18/26 才有的新 API，用 `#available` 做条件处理，老系统走降级路径。
- 团队里若有人只会 UIKit，两周 SwiftUI 上手期即可补齐——声明式思维对写过前端的人尤其友好。

SwiftUI 的"声明式"长什么样，看一段 16 行的问诊表单就懂：

```swift
struct ConsultFormView: View {
    @State private var carModel = ""
    @State private var faultText = ""

    var body: some View {
        Form {
            TextField("车型（如：卡罗拉 2021）", text: $carModel)
            TextField("描述故障现象", text: $faultText, axis: .vertical)
                .lineLimit(3...6)
            Button("提交问诊单") {
                // 调后端接口创建问诊工单
            }
        }
        .navigationTitle("故障问诊")
    }
}
```

没有手写"创建输入框、设置位置、响应事件"的步骤，只声明"这页有什么"。这就是它能省代码的原因。

## 第四章 技术选型③ 跨端——Flutter、React Native 还是双原生

### 4.1 三条路线是什么

| 路线 | 语言 | 一句话 | 比喻 |
|---|---|---|---|
| A. 双原生 | iOS 用 Swift、安卓用 Kotlin | 两套代码、两个团队/两个半人 | 请两位本地厨师各开一灶，味道最正、成本最高 |
| B. Flutter | Dart | 一套代码，自绘引擎把界面画得两端一模一样 | 中央厨房统一预制，两端味道完全一致 |
| C. React Native（RN） | JavaScript/TypeScript | 一套代码，底层渲染的是**真正的原生控件** | 统一采购本地食材，两端各像各的 |

### 4.2 当前事实（2026 年 11 月核验）

- Flutter 最新稳定版 3.50（2026-11-11 官方博客发布），配套 Dart 3.14；**直接原生互操作（Direct native interoperability）已转正**——Dart 可以直接调 Swift/Kotlin 代码，写原生桥更省事了。
- RN 最新版 0.88（2026-10-19 官方博客）；0.82 起新架构（Fabric 渲染 + JSI 通信）成为唯一架构，老架构已移除；官方文档主线推荐用 Expo 工具链起步。
- 两者在国内都有大量生产案例（Flutter：闲鱼等；RN：字节系多个产品）。选谁都不会踩"无人维护"的坑。

### 4.3 对比表（按决策重要度排序）

| 维度 | Flutter | React Native | 双原生 |
|---|---|---|---|
| 人力成本 | 一套代码，省 40~50% 客户端人力 | 同左 | 两套代码，人最多 |
| UI 一致性 | 两端像素级一致（自绘引擎 Impeller） | 用原生控件，两端有细微差异 | 各自最原生 |
| 性能 | 好（无 JS 运行时开销） | 新架构后差距已缩小 | 最好 |
| 国内三方插件（IM/地图/支付/推送） | 齐全 | 齐全（Expo 生态补足工具链） | 全部原生直连 |
| 热更新 | 安卓端可行；iOS 端受苹果审核条款限制，不要依赖 | 同左 | 同左 |
| 招聘 | Dart 冷门但上手快，可转岗培养；也可从前端转 | TS 前端供给大 | 各招一位原生，成本最高 |
| 和 Web/小程序复用 | Web 支持成熟但国内电商很少用 Flutter Web | 若团队会 React，Web 可部分复用 | 无复用 |

### 4.4 按你们的场景打分

你们的约束条件是：**双端都要、团队从零组建、人手大概率不多；聊天和商城都有成熟的三方能力；唯一"特殊"的蓝牙 OBD 交互，无论选哪条路都要写原生桥**。

- 人少 + 双端同步上线 → 跨端收益最大。
- 商城 UI 定制多、问诊表单多 → Flutter 的自绘一致性反而省掉"两端样式对不齐"的联调。
- 蓝牙、推送、支付、隐私合规这些**壳层代码**，跨端框架照样要写原生模块——所以选跨端 ≠ 不需要 iOS 原生能力，你作为 iOS 负责人的价值恰恰在这层。

### 4.5 建议

- **默认推荐：Flutter。** 国内插件生态最全、两端一致、招人可培养。这就是"跨端选 Flutter 还是 RN"的答案：两家都是成熟方案，**按团队背景选**——有 React/TS 存量团队选 RN（走 Expo），否则 Flutter。
- 如果未来公司明确要"一套代码跑 App+小程序+Web"，重新评估 RN 的 React 生态复用，不要现在为假设买单。
- **跨端后必须保留的原生清单**（写进 ADR 防止后人误判）：推送（APNs/厂商通道）、支付（微信/支付宝）、蓝牙 BLE 桥、隐私权限声明、开屏与热更逻辑、崩溃监控。

### 4.6 顺带说一句小程序

汽车服务用户的相当一部分动作发生在微信里（朋友转介绍、看店）。建议 1.x 阶段补一个**微信小程序**做轻量入口（问诊单预填、商城浏览），实现上与 App 共用后端。小程序与 App 是两条客户端线，别指望一套跨端代码同时出两端——那类方案在国内电商场景的体验代价不小。

## 第五章 需求排期怎么做（MVP 划分与迭代节奏）

### 5.1 三个原则

1. **闭环优先**：先让"提问→AI 问诊→下单→支付"整条链路能跑通，哪怕每个环节都很简陋；一个完美的聊天页救不了跑不通的闭环。
2. **价值排序**：每个需求标 P0（不做不能上线）/P1（上线后第一个月补）/P2（看数据再定）。
3. **留缓冲**：估时结果 ×1.5 起步；新组队、跨端新栈的团队按 ×2 算。排满的排期等于没有排期。

### 5.2 这个项目的 MVP 拆分建议

| 优先级 | 内容 | 说明 |
|---|---|---|
| P0（v1.0 必须） | 手机号一键登录 | 国内标配，见 7.4 |
| P0 | AI 问诊会话（文字+图片上传、流式回复、诊断卡片） | 业务起点；协议复用仓库七种消息（见 7.1） |
| P0 | "内容由 AI 生成"标识 + 免责声明 | 合规硬要求，见 6.5 与第十一章 |
| P0 | 商城（列表/详情/购物车/下单） | v1.0 只做自营配件 SKU |
| P0 | 微信+支付宝支付 | 实物商品走第三方支付（见 6.3 判断表） |
| P0 | 订单与物流查询 | 快递鸟/快递100 类聚合查询 |
| P0 | 个人中心 + 隐私合规全套 | 首启弹窗、权限说明、注销账号（见 6.5） |
| P1（v1.x） | OBD 报告接入、优惠券、真人客服、会员/次卡、会话历史管理 | 会员这类数字内容注意走 IAP（见 6.3） |
| P2（看数据） | AI 读视频、社区内容、数据看板、分销 | 全部先记需求池 |

### 5.3 迭代节奏

- **双周一个迭代**：周一需求评审 → 周二 UI 评审 → 开发+联调 → 后周提测 → 测试两天 → 预发验证 → 发布。
- **固定提审日**：每个版本定死"周四提审"。苹果常规审核通常一两天，以 App Store Connect 实际返回为准；安卓各家审核时长不一，预留 3 天以上。
- **版本号规则**：v1.0 上线，之后 v1.x 双周迭代，破坏性改动才升 v2。

### 5.4 工时怎么估（不拍脑袋）

**三点估算**：`期望工时 = (乐观 + 4×最可能 + 悲观) ÷ 6`。让实际写代码的人给三个数，负责人别代估。

粗估系数参考（页面复杂度）：

| 页面类型 | 单页估时 | 例子 |
|---|---|---|
| 静态展示 | 0.5 人日 | 协议页、关于我们 |
| 表单/列表 | 1~2 人日 | 问诊单、订单列表 |
| 复杂交互 | 3~5 人日 | 聊天页、购物车 |
| 新技术/硬件对接 | 5~10 人日起 | 蓝牙 OBD、视频通话 |

在页面估时合计之上，再加**联调 ×1.3、测试与修 bug ×1.2、缓冲 ×1.5**，才是能对外承诺的数字。听起来虚高？三个系数被吃光是常态，这就是"排期崩盘"的第一大原因。

### 5.5 里程碑示例（按双周节奏，示例供参照）

| 时间 | 阶段 | 出口标准 |
|---|---|---|
| 第 1~2 周 | 边界确认+MVP+选型 | 一页纸 PRD、选型 ADR 签认、慢手续全部递出 |
| 第 3~4 周 | 基建周 | 仓库/CI/三方服务打通；登录+首页骨架在真机跑通 |
| 第 5~10 周 | 三个双周迭代做 P0 | "问诊→AI 对话→下单→支付"全链路可演示 |
| 第 11 周 | 内测周 | TestFlight + 蒲公英分发；崩溃率达标、核心链路冒烟通过 |
| 第 12 周 | 提审上架 | iOS 与主流安卓商店过审上架 |
| 第 13 周起 | P1 迭代 | 每双周一个版本，看数据调优先级 |

### 5.6 变更纪律

迭代开始后插进来的新需求，默认进**下一个**迭代；插单的唯一例外是"致命缺陷或合规问题"。要插单就等价砍需求——排期是合同，不是愿望清单。

## 第六章 国内上架合规与支付（最容易翻车的一章）

### 6.1 资质全家桶与备案实操（对照 1.3 的表逐项打勾）

| 资质/手续 | 谁要求 | 没有的后果 |
|---|---|---|
| 营业执照 | 所有平台 | 一切无从谈起 |
| 域名 ICP 备案 | 国内服务器接入 | 网站与接口无法合规提供服务（公司已有网站，大概率已有，核实即可） |
| App 备案（工信部信管〔2023〕105号文） | 所有国内分发渠道 | 2024 年 4 月起，未备案的存量 App 已被处置下架；新 App 未备案不予分发 |
| 软件著作权证书 | 国内安卓商店（华为、小米等明文要求，应用名需与软著名称一致）；**App Store 不要求** | 安卓商店上架被驳回 |
| ICP 经营性许可/EDI（如引入第三方商家入驻） | 电商平台类业务 | 涉嫌无证经营，先过法务再开发 |
| 隐私政策（在线链接）+ 用户协议 | 所有商店 + PIPL（个人信息保护法） | 提审被拒、通报风险 |

> **新手常见疑问：iOS 上架需要软著吗？**
> **不需要。** App Store 审核不查软件著作权，苹果只看开发者账号主体与合规项。但**安卓商店需要**，你们双端一起上，所以软著照样要办——顺带它也是公司的知识产权资产，将来被抄袭维权时是关键证据。申请时把"软件全称"定成与 App 名称一致的命名，安卓提审时名字能直接对上。

**App 备案五步走**（公司已有网站，重点看第 1、2 步）：

1. **核实旧备案**：确认公司网站的 ICP 备案处于有效状态、备案主体与营业执照一致。App 备案是在同一主体下**新增一条 App 记录**——网站备案过 ≠ App 备案过，两回事。
2. **确认接入商**：App 备案由**网络接入服务提供者（服务器所在云厂商）或分发平台代为提交**。你们服务器在哪朵云上，就去那朵云的备案控制台发起，不用自己去管局排队。
3. **云厂商控制台提交**：选"App 备案"，填 App 名称、平台（iOS/安卓）、BundleID/包名、关联域名与服务器 IP，附营业执照与法人材料。
4. **确认与审核**：接入商初审通过后，主办者按短信提示登录 beian.miit.gov.cn 完成确认，随后由住所所在地省级通信管理局审核（几天到几周不等）。
5. **回填备案号**：拿到备案号后，在 App Store Connect 与各安卓商店后台的备案信息字段填入——**没有备案号，商店不予上架**。

**软著申请材料清单**（发起人：安卓负责人；渠道：中国版权保护中心官网，全程线上）

动手前先定好三件事：① 软件全称——与 App 上架名称保持一致（安卓商店按名称对应审查），版本号写 V1.0；② 开发完成日期与发表状态（还没上线可写"未发表"）；③ 从哪个代码仓库、用哪份文档截取鉴别材料。

| # | 材料 | 要求 | 从哪来 |
|---|---|---|---|
| 1 | 软件著作权登记申请表 | 官网在线填报后生成 | 版权中心官网 |
| 2 | 程序鉴别材料（源代码） | 前后各连续 30 页、共 60 页；程序每页不少于 50 行；整体不足 60 页就交全部；页眉标注软件名+版本号+页码 | 代码仓库导出 PDF，删掉含密钥的配置页与第三方库代码页 |
| 3 | 文档鉴别材料 | 任选一种：用户手册/操作说明书/设计说明书；前后各连续 30 页；文档每页不少于 30 行；要能看到功能界面截图 | App 真机/设计稿截图 + 功能说明 |
| 4 | 主体证明文件 | 营业执照（企业主体） | 行政 |

办理要点：账号注册 → 实名认证 → 在线填报上传 → 受理 → 审查 → 电子证书；**官费自 2017 年 4 月 1 日起停征（免费）**，代理加急才收费（数百到千元级）；普通流程等待数周到两个月，赶安卓上架就买加急档。两个坑：第三方开源代码混进鉴别材料会被退回；软件全称与 App 名称对不上会导致商店驳回（见 6.6 案例二）。

**App 备案材料清单**（发起人：后端负责人；渠道：服务器所在云厂商备案控制台）

前置条件按时序排（先看这条再动手）：**先把 Bundle ID 和安卓包名定死**——Bundle ID（Bundle Identifier，iOS 应用的全局唯一标识，反向域名格式，如 `com.公司名.应用名`）与安卓包名一经备案录入，变更要走变更备案流程；**先有正式签名的安装包**——公钥/MD5 是签名安装包的"指纹"（管局用它核对上架的包与备案的包是不是同一个），要从正式签名包提取，所以正确的时序是"v1.0 安装包出来 → 发起 App 备案 → 拿备案号 → 提审"，不是提审前才想起办。

| # | 材料 | 说明 |
|---|---|---|
| 1 | 主体信息 | 营业执照、法人及负责人身份证信息、手机号、应急联系人 |
| 2 | App 名称与图标 | 备案名要与各商店上架名一致 |
| 3 | 运行平台 | iOS / 安卓分开录入 |
| 4 | 包名 / Bundle ID | 安卓填包名，iOS 填 Bundle ID |
| 5 | 公钥与 MD5 值 | 从两端正式签名的安装包/签名证书提取 |
| 6 | 内嵌 SDK 清单 | SDK 功能类型与服务厂商信息——直接把 6.5 的三方 SDK 自查表拿来用 |
| 7 | 云资源 | 接入商名下可备案的服务器 |
| 8 | 前置审批文件 | 仅新闻/出版/教育/影视等特殊类目需要，汽车问诊不涉及 |

办理要点：全程在云厂商控制台操作，免费；主体核验 → 短信确认 beian.miit.gov.cn → 管局审核（几天到几周）→ 备案号回填商店后台。审核期间手机保持畅通，管局可能电话核验——这是常见的隐形延期原因。

### 6.2 苹果侧：账号与费用

- **公司账号**（Apple Developer Program）：年费 ¥688（官方中文页标价，约 99 美元/年），注册需 D-U-N-S 编码（免费）。App 会挂在公司法人主体名下——国内公司一律选这个，别用个人账号。
- **App Store Small Business Program（小型企业计划）**：年收入在门槛内的开发者，IAP 抽成从 30% 降到 15%。上线后记得申请。
- **TestFlight**：苹果官方内测分发，提审前用它给内部和种子用户装包。

### 6.3 收钱路线判断表（本章最重要的一张表）

苹果《App 审核指南》3.1.1 要求：**在 App 内解锁功能或数字内容（会员、课程、充值等）必须用 IAP**；3.1.3(e) 要求：**购买在 App 之外消费的实物商品或服务，必须用 IAP 以外的支付方式**。对照你们的业务：

| 你卖的东西 | 性质 | iOS 上怎么收钱 | 安卓上怎么收钱 |
|---|---|---|---|
| 配件、耗材（实物） | App 外消费 | 微信/支付宝（依据 3.1.3(e)） | 微信/支付宝 |
| 未来与修理厂合作的维修服务 | App 外消费（服务在店内完成） | 微信/支付宝（同上） | 微信/支付宝 |
| 会员、课程、付费资料包（数字内容） | App 内解锁 | 必须走 IAP，苹果抽成（小型企业计划 15%） | 微信/支付宝 |
| AI 问诊增值功能（若未来对深度诊断收费） | App 内解锁的功能 | 优先按 3.1.1 走 IAP；拿不准见下方说明 | 微信/支付宝 |

按当前业务（问诊免费、赚钱落在商城），苹果支付这条线上最省事，也最不容易踩条款。若未来对 AI 问诊的增值能力收费，它更接近"App 内解锁的功能"，而不是"App 外消费的服务"——**优先按 3.1.1 走 IAP**；或把付费购买放在网页端、App 内不出现价格与购买入口，具体边界以当期《App 审核指南》为准。**拿不准就在提审前在审核备注里写清业务说明，或走开发者技术支持工单确认**——比上线后被拒返工便宜得多。

### 6.4 安卓商店侧

- 各家审核独立：华为、小米等均要求软著；应用名称要与软著名称一致（变更要提供变更证明）。
- 多数商店要求**应用加固**（防反编译）与签名证书管理，加固用免费的厂商工具或腾讯加固等即可起步。
- **工信部常态化抽检**：违规收集个人信息会被通报、限期整改、下架。通报名单里每年都有大公司，别心存侥幸（见 6.5）。

### 6.5 隐私合规红线清单（上线前逐条自查）

1. **首次启动弹窗**：用户同意隐私政策前，不得初始化任何采集数据的 SDK（包括统计、推送）。
2. **权限最小化**：要相机权限才申请相机，要定位才申请定位；权限申请时机放在"用到的那一刻"，不是启动时全要一遍。
3. **SDK 自查清单**：维护一张"我们嵌了哪些三方 SDK、各收集什么"的表——第三方 SDK 的收集行为由你兜底（苹果审核指南明确要求开发者对其负责）。
4. **账号注销**：必须提供，且流程不得刁难。
5. **隐私政策**：内容与实际行为一致，链接可访问。
6. **AI 服务告知**：问诊对话与照片会经大模型服务商处理，属于个人信息委托处理——隐私政策需列明服务商与用途（法务把关委托协议），并在首启弹窗文案中体现；不要把用户证件类照片发给模型。

### 6.6 两个高频"报错"案例

**案例一：苹果审核被拒（Guideline 3.1.1）**

现象（Resolution Center 收到的信件节选）：

```
Guideline 3.1.1 - Business - Payments
We noticed that your app offers digital content/services that are
purchased within the app, but you are not using Apple's In-App
Purchase API.
```

原理（新手版）：你把"会员/付费咨询"这类数字内容放进了 App 内购买流程，而苹果规定这类内容只能走它的收银台。**怎么办**：① 对照 6.3 的判断表重新归类你的收费项；② 数字内容改走 IAP，或把购买移到 App 外；③ 在 Resolution Center 回复修改说明并附演示步骤。**预防**：版本评审时加一个固定检查项"本版本新增收费点走哪条支付路线"。

**案例二：安卓商店驳回（资质不全）**

现象（商店后台驳回原因）：

```
驳回原因：未提供《计算机软件著作权证书》或证书主体与开发者主体不一致
```

原理：安卓商店要求上架 App 的版权归属可查，软著主体必须和开发者账号主体对得上。**怎么办**：① 补交软著或《APP 电子版权认证证书》；② 名称不一致就按商店要求提供变更/关联证明；③ 应用名改到与软著一致。**预防**：软著申请时就把"软件全称"定成与 App 名称一致的命名，见 1.3 的手续表，这是第 2 周就该递出去的事。

## 第七章 第三方服务选型（聊天/支付/推送/登录/地图/监控）

### 7.1 聊天框架：AI 对话用云 IM 还是自建 WebSocket

先分清两种"聊天"：**用户 ↔ AI Agent 的对话**（你们的主场景），和**用户 ↔ 真人（客服）的聊天**（P1+ 才会有）。两类场景的最佳方案不同。

| 方案 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| 自建 WebSocket + 自定义消息协议 | 与 AI 流式输出天然契合：打字机效果、工具执行进度、诊断卡片、用户确认回执，全都用自定义消息类型表达，协议完全自主；零订阅费 | 连接可靠性自己负责（心跳/断线重连/离线补拉/消息序号）；后端要配好 Nginx 的 WebSocket 升级头这类运维细节 | **AI 对话为主（本项目）** |
| 云 IM SDK（腾讯云 IM/环信/融云） | 消息可靠性、漫游、多端同步、真人客服工作台都是现成的；以后加真人客服/车主群聊直接用 | AI 流式对话要塞进 SDK 的"自定义消息"里绕着做，打字机效果和卡片交互都别扭；套餐收费（专业版量级约千元/月起，以官网为准） | 真人聊天为主场景时 |
| SSE / HTTP 流式 | 实现最简单 | 单向通道，用户无法插话、取消、发卡片回执 | 只做网页演示 |

**建议：自建 WebSocket + 七种消息协议**——与仓库《Python后端开发知识体系》第六章、《Flutter聊天窗口与Agent接入知识体系》的既定结论一致：后端 FastAPI 已按 WebSocket 服务化设计，App 端照协议接入即可，不要另起炉灶。两个具体问题的落地方式：

- **AI 读图**：客户端把照片压缩后传对象存储（OSS/COS），消息里带图片 URL；Agent 侧交给支持视觉的模型读图。图片就是一种带 URL 的消息类型，协议不用改。
- **AI 看视频**：按你的决定先不做。将来若做，按"端上抽帧上传 + 多图消息"估（5~10 人日级别），别当小需求排进双周迭代。

真人客服需求出现时（P1+），先在同一条 WebSocket 协议里扩展"客服消息类型"起步；量大再评估引入云 IM 做客服模块，两套并存不冲突。

### 7.2 支付

- **微信 App 支付 + 支付宝 App 支付**：在开放平台创建移动应用、签约商户号，服务端下单签名，客户端拉起收银台。
- **iOS 数字内容另走 IAP**（见 6.3），IAP 的订单校验要做服务端二次验证，别只信客户端回执。
- 银联/聚合支付（如微信+支付宝一次接入的聚合 SDK）在量小的时候收益不大，先直连两家。

### 7.3 推送

- iOS 只有 APNs 一条路；安卓各厂商（华为/小米/OPPO/vivo/荣耀）各有一套推送通道，App 被杀后只有厂商通道能送达。
- 实际做法：接**聚合推送服务**（极光、个推、友盟等）统一对接 APNs + 各厂商通道，省掉逐家接 SDK 的维护量。

### 7.4 手机号一键登录

原理一句话：三大运营商提供"网关取号"能力（手机在流量网络下可静默识别本机 SIM 卡号），聚合 SDK 把三家打包成统一接口。

| 方案 | 优点 | 缺点 | 价格量级（官网核验 2026-11，以官网为准） |
|---|---|---|---|
| 阿里云号码认证（PNVS） | 三网聚合、按量阶梯计费便宜 | 高级能力较少、文档偏工具化 | 约 0.001~0.006 元/次阶梯 |
| 极光认证（JVerification） | 聚合三网、文档成熟、可与极光推送打包谈 | 单价明显更高 | 约 0.03~0.06 元/次阶梯 |
| 运营商直连（移动/联通/电信各自 SDK） | 成本最低，量大时常有免费额度 | 三家 SDK 全要接，机型与 SIM 场景适配烦 | 免费额度+低价 |
| 短信验证码（兜底，必配） | 取号失败时的唯一退路 | 成本高、转化低 | 按条计费 |

**建议**：v1.0 接聚合——拿月预估量让阿里云和极光各报一版价（阿里云 PNVS 价格优势明显）；一键登录失败自动回落短信验证码；日活上来后（月百万次级）评估换运营商直连省成本。

两个必测场景写进测试用例：**Wi-Fi 网络下取号必失败**（网关取号依赖运营商数据网络），要验证自动回落短信；**双卡/副卡/物联网卡/停机卡**取号会失败，回落路径同样要通——一键登录上线后被应用商店和用户吐槽最多的就是"回落没做好"。

### 7.5 地图与定位（门店/上门服务需要）

高德、腾讯、百度三家可选，先用免费额度开发，商用后按官网商务页签约。一个必懂的概念：国内地图使用 **GCJ-02 坐标系**（俗称"火星坐标"，在 GPS 原始坐标 WGS-84 基础上做了偏移）。服务端存哪个坐标系要一开始定死，否则"定位偏差几百米"这类事故会在联调期反复出现。

### 7.6 埋点、日志与崩溃监控

**埋点/行为统计**：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 友盟+（U-App） | 免费、国内统计标配，崩溃统计顺带覆盖 | 分析深度一般（漏斗/留存够用，精细化弱） | **v1.0 默认推荐** |
| 神策 | 分析能力强（漏斗/留存/ID-Mapping），可私有化部署、数据自主 | 商务报价不便宜，有实施成本 | 日活上万、要精细运营或数据必须私有化时再上 |
| GrowingIO | 增长分析见长 | 同类定价逻辑 | 与神策放一起比价 |
| 自研埋点 | 完全可控 | 报表、存储、查询全自己造，等于养一个数据组 | 起步不要 |

建议：友盟+ 起步，埋点命名规范自己定（见 8.5）——平台可以换，事件命名规范不能乱，日后迁移到神策历史事件名还能复用。

**端上日志**（排查"用户说有、复现不了"类问题的唯一手段）：

| 方案 | 优点 | 缺点 |
|---|---|---|
| Logan（美团开源，跨端含 Flutter） | 双端一套、压缩加密、延迟上报 | 开源社区维护节奏一般，需自己跟进适配 |
| CocoaLumberjack（iOS 原生） | 老牌稳定、多输出目标 | 仅 iOS，跨端要另接安卓方案 |
| 微信 xlog（mars） | 高性能、加密好 | 接入门槛略高 |

建议：小团队别自建日志平台。v1.0 做法＝**本地滚动日志（Logan 或 Lumberjack）+ 关键路径日志随崩溃/用户反馈一起上报**；日志里严禁打印手机号、token 等敏感信息（合规红线，见 6.5）。

崩溃监控：Bugly（腾讯，免费）或 Sentry（检索强、可自建）。**Firebase 全家桶在国内无法直连，不要把它当基础设施选型。**

### 7.7 存储、CDN、短信

- 图片/短视频/附件：对象存储（阿里云 OSS 或腾讯云 COS）+ CDN，客户端直传可省服务端带宽。
- 短信：阿里云/腾讯云短信服务，用于验证码兜底与订单通知。

### 7.8 OBD 盒子数据接入要点（P1 阶段启动前读一遍）

先和硬件负责人确认一个关键问题：**盒子的数据怎么到云端？** 这决定客户端工作量：

| 盒子形态 | 数据链路 | 客户端工作量 |
|---|---|---|
| 盒子自带网络（4G/Wi-Fi）直报云端 | 盒子 → 服务端 → App 展示故障报告 | App 只做报告展示页，无蓝牙代码 |
| 盒子只提供蓝牙（BLE） | 盒子 → App → 服务端 | App 要做 BLE 连接、指令收发、后台保活，5~10 人日起 |

蓝牙形态下的必做项：

- iOS 权限声明（缺了直接闪退，商店审核也会拦）：

```xml
<!-- Info.plist -->
<key>NSBluetoothAlwaysUsageDescription</key>
<string>用于连接 OBD 设备读取车辆故障数据</string>
```

- iOS 后台持续收蓝牙数据需要配置后台模式 `bluetooth-central`；安卓 12 起蓝牙扫描需要运行时权限（`BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT`）。
- 蓝牙连接、OTA 升级的完整实战见仓库内《iOS蓝牙设备连接与OTA固件升级知识体系》。

无论哪种形态，OBD 故障数据最终都作为 AI 问诊的上下文输入（消息协议里是一条带结构化数据的消息发给 Agent），与后端在协议联调时对齐字段。

## 第八章 工程基建与团队配置

### 8.1 分支与评审

从 0 起步用最简模型：`main` 保护 + 功能分支 + 合并前至少一人评审。别一上来就上复杂分支流，纪律比模型重要。

### 8.2 CI/CD 选型与内测分发

iOS 侧三个候选：

| 方案 | 优点 | 缺点 | 费用（官网核验 2026-11） |
|---|---|---|---|
| Xcode Cloud | 零运维、证书签名托管、与 TestFlight/App Store Connect 无缝衔接 | 只服务 iOS；复杂脚本能力弱；偶有排队等待 | 开发者会员含 **25 计算小时/月**；100 小时档 49.99 美元/月，250 小时档 99.99 美元/月 |
| Jenkins + Fastlane（自建 Mac mini） | 完全可控；iOS/安卓共用一台机器；加固、多渠道等任意脚本都能挂 | 要人维护（系统升级、证书、磁盘），搭建 2~3 天起步 | 一台 Mac mini + 人力 |
| 托管 CI 的 macOS runner（GitHub Actions 等） | 无硬件、配置即代码 | macOS 计费远贵于 Linux runner；代码在境外平台有合规顾虑（国内公司多为私有 GitLab） | 按分钟计费 |

**建议**：iOS 用 Xcode Cloud 起步——双周迭代加测试包的构建量在免费额度内基本够用，超出再升 100 小时档或转自建 Jenkins；安卓用 GitLab CI 或 Jenkins（安卓打包不需要 Mac，普通 Linux runner 即可，加固步骤可挂流水线）。

**内测分发**：iOS 走 TestFlight（Xcode Cloud 可自动送测），安卓走蒲公英（pgyer.com）或商店内测渠道。

标准动作：合并到 main 自动出包，每天一版可安装包——"能随时装到手机上"是减少联调扯皮的最低成本手段。

### 8.3 架构分层（大白话三层楼）

| 层 | 职责 | 大白话 |
|---|---|---|
| UI 层 | 页面与组件（SwiftUI 视图） | 只管"长什么样" |
| 业务层 | 状态与流程（问诊单状态机、购物车逻辑） | 只管"什么时候发生什么" |
| 数据层 | 网络请求、缓存、本地库 | 只管"数据从哪来到哪去" |

按业务模块（问诊/聊天/商城/我的）拆包，模块间只通过接口调用。这个规模不需要更花哨的架构，管住"UI 层不直接摸数据库"就赢过多数新项目。

### 8.4 环境与发布

- 四套环境：dev（开发）/test（测试）/staging（预发）/prod（生产），客户端可切换但默认隐藏入口。
- **灰度发布**：新版本先放 5~10% 用户（安卓商店支持分阶段放量；iOS 用分阶段更新），崩溃率正常再全量。
- **强制更新**：电商类 App 必备——接口下发最低可用版本，低于版本强升，配合后端"改坏了能勒住全量用户"的保险绳。

### 8.5 埋点与数据

先定事件命名规范再开发（`page_module_action` 风格）。v1.0 必埋：注册转化、问诊提交、AI 首次响应时长、图片上传成功率、下单转化、支付成功。这些就是第 5 章里 P2 需求"看数据再定"的数据来源。

### 8.6 选型文档（ADR）模板要点

一页纸，五个字段：**背景**（为什么做决策）/ **候选**（列 2~3 个选项）/ **决定**（选了谁）/ **后果**（好处 + 接受的代价）/ **复核时间**（什么条件触发重评，比如"RN 新架构生态稳定半年后重评跨端方案"）。选型会被后人挑战，ADR 就是你的挡箭牌。

### 8.7 最小团队配置

| 角色 | 人数 | 备注 |
|---|---|---|
| iOS 负责人（你） | 1 | 选跨端则同时是 Flutter 主力 |
| 安卓工程师 | 0~1 | 跨端可省；留 0.5 人精力给原生桥 |
| 后端 | 2 | 含 IM 服务端对接与支付回调 |
| UI/UX | 1 | 可与设计外包并行 |
| 测试 | 1 | 前期可由开发兼任，上线前必须专职 |
| 运营/法务 | 借力 | 备案材料、协议、资质走公司通道 |

## 第九章 常见坑与排查

> 共同规律：从 0 到 1 的项目，故障大头在"手续与审核"，其次在"三方服务集成"，最后才是代码本身。

### 9.1 公司开发者账号卡在 D-U-N-S

**现象**：注册 Apple Developer Program 时提示无法验证公司信息，或 D-U-N-S 申请后杳无音信。

**原理（新手版）**：苹果用邓白氏编码核实"你们公司真的存在"，而公司注册信息（英文名、地址、电话）如果和工商登记对不上，就会被卡住。

**怎么办**：① 登录 Apple 官网开发者账户页查 D-U-N-S 申请进度；② 核对营业执照英文名/拼音名、注册地址、联系电话是否一致；③ 用公司邮箱（非 QQ/163 个人邮箱）发起申请；④ 超两周无进展就回复邓白氏/苹果的跟进邮件催办。

**预防**：入职第一周就递 D-U-N-S 申请（见 1.3），别等代码写完。

### 9.2 苹果审核 3.1.1 被拒

见 6.6 案例一。预防手段是把 6.3 的收钱判断表放进版本评审清单。

### 9.3 安卓商店驳回（缺软著/备案号）

见 6.6 案例二。预防手段是软著早申请、App 名称与软著名称对齐。

### 9.4 上线后被通报"违规收集个人信息"

**现象**：工信部通报名单、商店限期整改通知，或用户投诉"没同意隐私政策也收到短信"。

**原理**：通常是三方 SDK 在用户同意前就初始化采集，或隐私政策写的和实际收集的不一致。

**怎么办**：① 对照通报项逐条自查，重点查 SDK 初始化时机；② 把所有采集 SDK 的初始化挪到"同意隐私政策之后"；③ 更新隐私政策并复测；④ 整改报告按通知渠道提交。

**预防**：CI 里加"隐私检查清单"步骤；新接任何 SDK 前先过 6.5 的红线清单。

### 9.5 AI 对话消息乱序或丢失

**现象**：用户反馈"消息时有时无""顺序乱了""AI 看不到我发的图"。

**原理（新手版）**：消息可靠投递依赖"客户端本地库 + 服务端全局序号（seq）+ 确认重传"三件套，自研最容易漏的是 seq 排序和离线补拉。用云服务 IM 仍可能在"本地会话表设计"上踩坑。

**怎么办**：① 检查消息表是否以"会话 ID + seq"为主键排序，而不是本地时间戳；② 排查离线补拉逻辑（重登后先拉 seq 增量）；③ 云服务 IM 就查 SDK 的消息同步回调用法是否正确。

**预防**：聊天页上线前做弱网测试（飞行模式切换、2G 模拟）。

### 9.6 蓝牙后台断连

**现象**：OBD 盒子在前台读数正常，切到后台几秒就断。

**原理**：iOS 对后台活动收得很紧，没声明蓝牙后台模式就活不过几秒。

**怎么办**：① Xcode 里 Target → Signing & Capabilities → Background Modes 勾选 `Uses Bluetooth LE accessories`（对应 Info.plist 的 `bluetooth-central`）；② 确认权限描述文案完整（见 7.8）；③ 安卓侧检查前台服务与蓝牙权限版本适配。

**预防**：硬件联调排期里把"后台场景"列为必测项，别只测前台。

### 9.7 排期崩盘

**现象**：三个双周迭代过去，P0 还剩一半。

**原理**：通常是估时没乘系数（5.4）、需求插单没纪律（5.6）、跨端新栈学习成本被低估三条叠加。

**怎么办**：① 当场砍范围保闭环：P0 里再挑 P0；② 插单需求清出本迭代；③ 里程碑重排并同步给老板——早说比晚说代价小得多。

**预防**：每个迭代结束做 15 分钟复盘，对比"估时 vs 实际"，两周就能校准出你们团队的真实系数。

### 9.8 支付联调失败（拉不起收银台 / 付了钱订单没变）

**现象**：客户端拉起微信收银台报"商家参数格式错误"；或用户已付款，App 里订单仍显示"待支付"。

**原理（新手版）**：支付由"客户端拉起 + 服务端回调"两半组成，任何一半对不上都会翻车。最高频的三处：开放平台填的应用签名/包名与实际安装包不一致；支付回调地址不在公网上（本地开发环境收不到微信/支付宝的通知）；回调到了但服务端验签失败或没做幂等。

**怎么办**：① 微信开放平台核对应用包名与应用签名（安卓签名证书的 MD5），苹果侧核对 Universal Link 配置；② 回调地址必须是公网可达的 https 域名——本地联调就部署到测试环境再测，不要指望真机连本机；③ 服务端按官方指引验签，并对回调做幂等处理（同一单重复通知只生效一次）；④ 用商户后台对账单核对实际到账。

**预防**：联调期就用 0.01 元真实支付把"下单→支付→回调→订单状态更新"全流程跑通——沙箱环境通过 ≠ 线上能通。

## 第十一章 进阶与业务视角——还该想到的问题清单

新手负责人最容易漏的问题，逐条过一遍：

| 问题 | 一句话建议 |
|---|---|
| 客服体系 | 纯 AI 兜底撑不住情绪类投诉：P1 起配人工客服，云 IM 服务商自带客服工作台 |
| 平台责任 | 只卖自营先不涉及；引入第三方商家入驻前过法务（电商法的平台经营者义务） |
| 发票 | 商城订单要开发票，接电子发票服务，别等用户投诉 |
| 应用名称与商标 | 上架前查商标（名称被注册会遭投诉下架），商店搜索确认重名 |
| 加急审核 | 苹果支持加急审核申请（有次数限制），大版本赶节点时用；安卓商店无此机制，多留时间 |
| 数据资产归属 | 三方服务（统计/存储/AI 服务商）的数据导出与迁移条款签约前看清，防止后期被锁死 |
| 防刷与风控 | 商城优惠券、一元购是羊毛党目标；下单接口做设备指纹与频控 |
| 无障碍与深色模式 | 商店审核加分项，SwiftUI 基本自动适配深色，成本很低 |
| 应用加固与防逆向 | 安卓上线前加固；iOS 侧敏感逻辑放服务端 |
| 灾备 | 支付回调、AI 服务这类"挂了就停业"的依赖，确认云服务商的 SLA（Service Level Agreement，服务等级协议——云厂商承诺的可用性与赔付条款）与多可用区方案 |
| AI 合规 | 聊天界面标明"内容由 AI 生成"（显式标识），接入已完成备案的大模型服务——四部门《人工智能生成合成内容标识办法》对显式/隐式标识有明确要求 |
| AI 成本 | AI 问诊的模型调用是持续可变成本：给单次会话设轮数与 token 上限，后台做月度成本看板，超阈值告警 |
