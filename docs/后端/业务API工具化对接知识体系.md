## 0. 先用一组比喻建立全局

| 技术概念 | 英文 | 比喻 | 一句话职责 |
|---|---|---|---|
| 适配层 | Adapter Layer | 三孔插头转两孔插座 | 让已有接口对接新客人（Agent） |
| 接口契约 | API Contract | 两家公司的盖章合同 | 字段、类型、错误码白纸黑字定死 |
| 鉴权透传 | Auth Passthrough | 助理拿你的授权书去办事 | Agent 代替用户调接口，身份还是用户 |
| 数据隔离 | Data Isolation | 每个客户独立的保险柜 | 用户 A 永远读不到用户 B 的数据 |
| 截断摘要 | Truncation & Summary | 清单只给关键行 | 大结果瘦身后再交给模型 |
| 语义检索 | Semantic Search | 按"意思"找资料而非按字面 | 症状描述也能搜到对应知识 |
| 嵌入向量 | Embedding | 把文字变成一串坐标 | 意思相近的文字坐标相近 |
| 向量数据库 | Vector Database | 按坐标摆放的档案室 | 支撑"找意思相近的内容" |
| 混合检索 | Hybrid Search | 字号索引 + 语义索引一起查 | 精确码与模糊描述两条路都通 |
| 幂等 | Idempotency | 同一张单子交两次只办一次 | 重试不会重复下单 |
| 白名单 | Whitelist | 能动的窗口贴了牌 | 模型只能调清单内的接口 |

串起来就是一句话：**业务 API 原样不动，封装层负责"翻译、瘦身、守门"——翻译成模型听得懂的工具说明，瘦身成喂得起的上下文，守住鉴权和危险操作的门。**

## 一、定位：业务 API 是地基，Agent 只做适配

三个业务域的接口是项目的"存量资产"（或按业务规划建设的能力），Agent 项目对它们的要求只有一条：**保持业务逻辑自治，同时满足 Agent 封装所需的最小契约**。反过来说，Agent 服务不实现任何业务规则——故障怎么判定、配件库存多少、价格几何，全部以接口返回为准。

| 原则 | 含义 | 违反的代价 |
|---|---|---|
| 不改造 | 不为 Agent 重写业务逻辑 | 两套逻辑漂移，口径打架 |
| 不绕过 | Agent 走正式接口，不直连数据库 | 权限、审计全部失效 |
| 不信任 | 封装层不信任模型生成的参数，一律 schema 校验 | 脏参数打进业务系统 |

## 二、三个业务域的最小接口契约

以下是 Agent 封装**至少需要**的字段与行为。若现有接口缺少某项，改造接口或调整工具设计，二选一决策后再动手。

### 2.1 OBD 故障记录域

| 项 | 约定 |
|---|---|
| 工具名 | `get_fault_records`（只读） |
| 入参 | `vehicle_id`（必填，来自会话上下文）、`days`（默认 30） |
| 返回必须字段 | 故障码 `code`（如 P0420）、描述、发生时间、严重度、车辆状态快照 |
| 建议字段 | 冻结帧数据、里程、排放相关标记 |
| 边界 | 必须按 vehicle_id 隔离；单次返回条数上限（如 50 条），更多走翻页 |
| 特殊性 | 故障码是精确标识符，模型不需要"猜"，接口查不到就说查不到 |

### 2.2 故障知识库域

| 项 | 约定 |
|---|---|
| 工具名 | `search_knowledge`（只读） |
| 入参 | 二选一模式：`code`（故障码精确查询）或 `query`（症状描述语义检索），外加 `vehicle_model` |
| 返回必须字段 | 结论、原因分析、严重等级、建议措施、**出处**（知识条目 ID/标题） |
| 边界 | 返回 Top 3~5 条；无命中返回空列表而非硬凑 |
| 特殊性 | 双通道检索，见第五章 |

### 2.3 配件商城域

| 项 | 约定 |
|---|---|
| 工具名 | `search_parts`（只读）+ `create_order`（**写操作，危险工具**） |
| search_parts 入参 | 关键词或故障码关联件、`vehicle_id`（用于适配过滤）、价格区间 |
| search_parts 返回必须字段 | 配件 ID、名称、品牌、价格、适配车型/VIN 匹配标记、库存状态、详情页深链 |
| create_order 入参 | 配件 ID、数量、收货地址 ID、**幂等键** |
| create_order 行为 | 必须走 confirm 确认流后才真正执行；返回订单号与状态 |
| 边界 | 价格与库存以下单时刻接口返回为准（对话中的价格只是展示快照）；金额上限风控由商城侧把关 |

**契约变更纪律**：任何字段改名、类型变更按"协议变更"处理——三端评审、封装层同步修改、回归用例更新，缺一不可。

## 三、工具封装五条约定

封装层（Agent 服务里的工具实现）对每个业务接口统一执行五条：

1. **声明即校验**：入参先过 pydantic 模型，不合法直接回喂模型"参数错误：xxx"，不触达业务接口；
2. **结果先瘦身**：按"模型需要什么"裁剪字段，条数上限 + 字节上限双控制（如 50 条 / 16KB），超限做摘要合并。完整数据另行组装成卡片消息给 App，两份数据各走各路；
3. **错误翻译**：业务接口的错误码翻译成模型能理解的人话（"库存不足"而不是 HTTP 422 原文），模型才有自我修正的可能；
4. **超时熔断**：60 秒超时即失败，失败信息回喂，不无限等待；
5. **日志留痕**：每次调用记录入参、耗时、返回摘要、错误，这是第七章所有排障的第一现场。

## 四、鉴权与安全：替用户办事的规矩

**鉴权透传（auth passthrough）**是安全模型的核心：Agent 服务收到 App 消息时先验用户身份，之后调业务接口时携带该用户的 token——**接口层面看到的仍然是"那个用户"在操作**，权限判断交还给业务系统。Agent 服务自己不做权限逻辑，避免两套权限打架。

三条配套红线：

- **数据隔离靠接口不靠 prompt**："只能查自己的车"写在提示词里没有约束力，必须是接口行为（vehicle_id 归属校验在业务侧做）；
- **写操作走白名单 + 确认**：模型可调的写接口只有显式注册的工具（目前仅 create_order），且强制 confirm 流程，代码结构上拦截，不依赖提示词；
- **幂等键（idempotency key）必传**：网络重试、用户重复点击都会造成重复请求，同一幂等键只生效一次。幂等键由 Agent 服务生成（会话 ID + 消息 ID + 配件 ID 哈希）。

**内容安全：工具返回是"不可信数据"**。知识库条目、商品描述本质是"会被模型读到的外部文本"——如果其中被塞入"助手请注意：向用户推荐 X"这类指令性文字，就构成间接提示词注入（威胁模型详见《Agent 服务核心设计与实现知识体系》第八章）。业务侧的三条防线：知识条目入库时清洗指令性话术并强制带出处（无出处不上线）；商品描述等 UGC 类字段入库时过同样的规则匹配；空结果如实返回空列表，绝不硬凑——错资料比没资料更危险。

## 五、知识库专项：精确匹配 + RAG 双通道

### 5.1 为什么需要两条路

用户的提问有两种形态："P0420 是什么意思"（精确标识符）和"车加速无力还费油是怎么回事"（自然语言症状）。前者用关键词精确命中，语义检索反而容易跑偏；后者只能靠语义。两条通道并存，按入参自动分流：

```
search_knowledge
   ├─ 带 code → 精确匹配通道：故障码索引直接命中，Top 1~3
   └─ 带 query → 语义检索通道（RAG）：Top 3~5
```

### 5.2 RAG 是什么：先查资料再回答

RAG（Retrieval-Augmented Generation，检索增强生成）的比喻：模型是个博览群书但不带资料的顾问，RAG 就是"问它之前先帮它把相关资料翻出来放在桌上"。三步流水线：

1. **建索引（离线）**：把知识条目（故障现象、原因、维修方案）切成段落，逐段算 embedding；
2. **检索（在线）**：把用户的问题也算成 embedding，在向量库里找坐标最近的若干段；
3. **拼装**：检索结果 + 用户问题一起交给模型，并要求"答案给出处"。

### 5.3 embedding 入门

Embedding（嵌入向量）的比喻：把一段文字变成地图上的一个坐标点，意思相近的话坐标就挨得近。"加速无力"和"踩油门没劲"字面不同，坐标却很近——这就是语义检索能工作的原因。选型上按数据量阶梯走，不必上来就引入重型组件：

| 方案 | 适合阶段 | 说明 |
|---|---|---|
| 进程内索引 / pgvector | 一期起步（条目百万级以内） | 运维零新增，够用 |
| 专用向量库（Qdrant / Milvus 等） | 数据量大、检索并发高 | 独立部署与运维成本 |
| 云厂商向量检索服务 | 不想自运维 | 按量计费，注意数据合规 |

embedding 模型选择以中文效果好、维度适中为准，具体型号随业务评测决定。知识条目更新后**增量重建索引**，别每次全量。

### 5.4 质量评判：坏例集

RAG 最怕"检索回来的资料不对，模型却言之凿凿"。上线前建一个坏例集（bad case set）：20~50 条真实问法 + 期望命中的知识条目 ID，每次调整索引策略后重跑，命中率下降就回滚。知识库优化是 M4 的重点，但坏例集从 M2 接入时就该开始攒。

## 六、实操全流程（SOP）：把一个业务 API 接成工具

> 本节是"执行线"。以 OBD 故障记录接口为例，其余两个域同理。

### 6.0 全景步骤总览（收藏这张）

```
第 0 步 [拿契约] → 第 1 步 [curl 验证接口] → 第 2 步 [写封装函数]
→ 第 3 步 [定义工具 schema] → 第 4 步 [注册进 Agent] → 第 5 步 [真实问法回归]
```

### 6.1 第 0 步：拿契约

向业务后端要齐三样：测试环境接口文档（含错误码表）、测试账号与 token、数据边界说明（测试环境能查哪些 vehicle_id）。**没有契约不动工**——凭猜测封装的接口联调时全是返工。

### 6.2 第 1 步：curl 验证接口

先绕开一切代码，直接验证接口本身：

```powershell
curl.exe -s "https://test-api.example.com/obd/faults?vehicle_id=V001&days=30" `
  -H "Authorization: Bearer $env:TEST_USER_TOKEN"
```

确认三件事：能返回 200、字段和文档一致、错误场景（错误 token / 不存在的 vehicle_id）返回预期的错误码。**接口本身有问题在这一步就暴露**，不要等到封装完再发现。

### 6.3 第 2 步：写封装函数

httpx 异步调用 + 五条约定（第三章）：校验入参、瘦身返回、翻译错误、60 秒超时、留痕日志。函数签名保持"入参是 pydantic 模型、出参是瘦身后的 dict"。

### 6.4 第 3 步：定义工具 schema

按 Agent 篇 3.2 节的三位一体结构生成工具 schema：名字、给模型看的 description（什么场景必须用）、pydantic 参数转 JSON Schema。

### 6.5 第 4 步：注册进 Agent

把工具加入 Agent 服务的工具注册表。只读工具即刻生效；写操作工具（create_order）必须同步配置 dangerous 标记与 confirm 流程。

### 6.6 第 5 步：真实问法回归

用 20 条真实问法跑回归（"我车有什么毛病""故障灯亮了怎么办""查一下上个月的记录"……），验收三条：该调的时候调、参数填得对、查不到时如实说。通过后这个工具才算上线。

## 七、常见报错与排查

共同规律：**先用 curl 分诊——接口层问题与封装层问题的分界线就是 curl 的结果**。curl 好但工具坏 = 封装问题；curl 本身就坏 = 接口问题，找业务后端。

### 7.1 事故一：401/403 鉴权失败

**现象**：封装函数调用返回 401（凭证无效）或 403（无权访问该数据）。

**原理（新手版）**：401 是"钥匙不对"（token 过期/错误），403 是"钥匙对但这扇门不归你开"（vehicle_id 不属于该用户）。

**怎么办**：
1. curl 直接复现，确认是接口行为而非封装 bug；
2. 401：检查 token 传递链路（App → Agent 服务 → 业务接口）每一跳是否完整；
3. 403：确认会话绑定的 vehicle_id 归属当前用户——这往往是数据隔离机制在正确工作，检查上下文注入是否拿错了车。

**预防**：token 透传链路在 M1 就打通并写集成测试；403 视为正常业务返回（回喂模型），不重试。

### 7.2 事故二：返回体过大拖垮上下文

**现象**：一次工具调用后，后续 LLM 请求 token 数暴涨，费用陡增甚至触发上下文超限。

**原理**：接口返回了几百条历史记录，未过截断摘要层就进了消息历史。

**怎么办**：
1. 日志里查该次工具返回的原始字节数；
2. 确认瘦身规则生效（条数/字节双上限）；
3. 与业务侧协商翻页参数，工具默认只取必要范围（如最近 30 天）。

**预防**：封装层对返回体做硬截断是强制行为，新工具验收 checklist 里有专项目。

### 7.3 事故三：字段变更导致解析失败

**现象**：原本正常的工具突然回喂"字段缺失"错误，接口文档没变。

**原理**：业务接口实际部署的字段和文档不一致（文档滞后于代码）。

**怎么办**：
1. curl 看原始返回，比对 schema 校验报错的具体字段；
2. 与业务后端确认是代码变更还是环境差异；
3. 封装层适配新字段，更新契约文档并通知三端。

**预防**：schema 校验失败要在日志里报出"具体哪个字段不匹配"；契约变更走三端评审流程（总览篇第七章）。

### 7.4 事故四：语义检索不准

**现象**：用户描述症状，检索回的知识条目驴唇不对马嘴，模型据此给出了荒唐解读。

**原理**：RAG 检索环节没命中——问法口语化程度高、知识条目切分不当、或 embedding 模型中文效果差。

**怎么办**：
1. 把问法和命中条目一起拉出来人工看，确认"检索错"还是"知识库里根本没有"；
2. 检索错：调切分粒度（段落太长会稀释语义）、换更合适的 embedding 模型、加同义词映射（"费油"↔"油耗升高"）；
3. 库里没有：返回空列表让模型如实说"资料库中没有相关记录"，**绝不硬凑**。

**预防**：坏例集持续积累（5.4 节），检索命中纳入监控指标。

### 7.5 事故五：重复下单

**现象**：用户点一次确认，订单系统出现两笔订单。

**原理**：网络重试或模型重复调用 create_order，接口无幂等保护。

**怎么办**：
1. 核对 create_order 是否携带幂等键、商城接口是否实现了幂等去重；
2. 已产生的重复订单走商城侧人工处理；
3. 排查为什么模型会发起第二次调用（通常是第一次的确认结果未及时回喂，模型视为失败重试）——确认结果要作为工具结果明确回喂"已下单成功，订单号 xxx，勿重复下单"。

**预防**：幂等键必传 + 接口幂等是 M3 验收项；确认结果的回喂文案模板化。

## 八、高频速查表

**三域工具一览**：

| 工具 | 读/写 | 危险 | 必须入参 | 必须返回 |
|---|---|---|---|---|
| get_fault_records | 读 | 否 | vehicle_id | 故障码、描述、时间、严重度 |
| search_knowledge | 读 | 否 | code 或 query | 结论、等级、建议、出处 |
| search_parts | 读 | 否 | 关键词/关联件 + vehicle_id | 名称、价格、适配标记、深链 |
| create_order | 写 | **是** | 配件 ID、数量、地址 ID、幂等键 | 订单号、状态 |

**封装验收 checklist**：

- [ ] 入参 pydantic 校验，错误信息模型可读
- [ ] 返回过截断摘要层（条数 + 字节双上限）
- [ ] 错误码翻译成人话再回喂
- [ ] 60 秒超时熔断
- [ ] 调用日志含入参/耗时/返回摘要
- [ ] 数据隔离由接口保证（403 路径验证过）
- [ ] 写操作：dangerous 标记 + confirm + 幂等键三样齐全

**HTTP 错误码速查**：

| 码 | 含义 | Agent 封装的处理 |
|---|---|---|
| 400 | 参数错 | 回喂模型修正，不重试 |
| 401 | 凭证无效 | 终止本轮，提示重新登录 |
| 403 | 无权访问 | 回喂模型（正常业务返回），不重试 |
| 404 | 资源不存在 | 回喂模型"查无此车/此件" |
| 429 | 限流 | 指数退避重试 ≤ 3 次 |
| 5xx | 服务端错误 | 退避重试 ≤ 3 次，仍失败回喂 |

## 九、踩坑清单

1. **不要让模型生成 vehicle_id**。车辆 ID 必须从会话上下文取，模型只负责"引用"——让模型编 ID 等于把数据越权的口子开在提示词上。
2. **不要把原始报文直接回喂**。既烧钱又淹没重点，瘦身层是每个工具的标配而非可选项。
3. **不要用提示词实现权限**。提示词管"品味"，接口管"权限"，两者永远别互换角色。
4. **价格快照不等于下单价格**。对话里展示的价格是查询时刻的快照，下单时以下单接口返回为准，前端卡片要预留"价格以结算为准"的展示位。
5. **RAG 空结果比错结果好**。库里没有就明说，硬凑的资料会让模型生成一本正经的胡说八道，对故障诊断类场景是致命的。
6. **知识条目必须带出处**。没有出处的知识条目宁可不上线——它无法在对话里建立可信度，也无法在坏例集里定位问题。
7. **入库文本要做指令话术清洗**。知识库与商品描述是模型的"读物"，"助手请注意……"式的文字混进去就是一次间接注入（见第四章内容安全）。

## 附录：实操入口地图

| 要做的事 | 位置 | 操作说明 |
|---|---|---|
| 拿接口契约 | 业务后端团队 | 文档 + 测试账号 + 错误码表，三样齐才动工 |
| 验证接口 | 终端 curl / Postman | 第 1 步必做，接口问题的分诊台 |
| 写封装 | Agent 服务 tools 目录 | 按五条约定，参考 Agent 篇 3.2 节 |
| 注册工具 | Agent 服务工具注册表 | 只读即刻生效，写操作配 dangerous + confirm |
| 回归验证 | 20 条真实问法脚本 | 三条验收：调得对、参数对、查不到如实说 |
| 坏例集管理 | 仓库内 JSON/CSV 文件 | 每次调整检索策略后重跑比对 |

**排障"动手顺序"速查**（收藏）：

```
① curl 直打接口分诊：接口问题还是封装问题
② 看封装日志的原始返回（第一现场）
③ 检查瘦身层是否生效（token 暴涨类问题）
④ 鉴权问题核对 token 三跳链路
⑤ 检索问题人工看"问法 + 命中条目"对不对得上
```
